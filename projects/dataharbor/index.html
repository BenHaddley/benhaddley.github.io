OPTECH DataHarbor

Creator · 2026 · 6 min read

A local-first research gateway that puts personal documents, an offline Wikipedia/Stack Exchange mirror, live web search, and a local AI summarizer behind one search bar — fully self-hosted, with no cloud dependency and no query ever leaving the machine.

Overview

OPTECH DataHarbor is a Docker Compose stack of eight services that unifies research across three normally-separate worlds — personal documents, an offline reference library, and the live web — behind a single search bar, with an on-device model summarizing results and a purpose-built database surfacing country capability data inline whenever a nation is mentioned in a query.

Problem

Research on a given topic normally means switching between three unconnected tools: a handful of local PDFs and Word docs, a reference site half-remembered, and a general web search to fill the gaps — none of which know about each other, and none guaranteed to work without a live internet connection. For research that's geopolitical or defence-adjacent, sending every query to a cloud search engine or AI service isn't a comfortable default either.

Constraints

  • Every source had to be genuinely searchable from one place — not three browser tabs — without collapsing the fact that a hit from local documents, an offline encyclopedia, and the live web all carry different reliability
  • Had to keep working with no internet connection at all: local documents and the offline reference library can't depend on connectivity
  • The one AI feature (summarizing results) couldn't send query text or result content to a cloud API — it had to run entirely on-device
  • Live web search had to go through a source that doesn't track or profile the query, not a conventional search API
  • A general news RSS pull is mostly noise for this use case — needed relevance filtering that doesn't require a heavyweight NLP pipeline

Approach

The stack splits cleanly by concern. Meilisearch handles hybrid full-text plus vector search over local documents and news, using a HuggingFace embedding model (BAAI/bge-small-en-v1.5). Kiwix serves a library of offline ZIM files — Wikipedia slices, several Stack Exchange communities, an OPSEC manual, a military medicine reference — so the reference library works with no network at all. SearXNG provides live web search without becoming a tracking vector itself. A watchdog-based ingest daemon auto-extracts and indexes any PDF, DOCX, TXT, Markdown, or HTML file dropped into an inbox folder. A news poller pulls curated geopolitical/defence RSS feeds through a keyword relevance gate. A FastAPI and SQLite countries service builds a nation capability database — population, GDP, military spending, personnel, alliance membership — from RestCountries and World Bank data. A single nginx-served frontend ties all of it into one search bar with source filters, and a local Ollama model (llama3.2:1b) streams a plain-language summary of the top results directly in the browser.

Key Decisions

Keyword-gated relevance filtering on the news feed instead of indexing every article

Reasoning:

A raw pull of "world news" RSS feeds is mostly not relevant to defence/geopolitical research — it's sports and entertainment next to the occasional story that matters. Rather than build an NLP classifier, general-purpose feeds (BBC, Reuters, Al Jazeera) are gated through a deliberately curated keyword allowlist covering military organisations, hardware, conflict events, and named geopolitical actors, while narrowly defence-focused sources (USNI News, Defense One) skip the gate entirely since everything they publish is already relevant.

Alternatives considered:
  • Index every article from every feed and rely on search ranking alone
  • Build a machine-learning relevance classifier

A hand-built alias table for country detection instead of requiring exact country names

Reasoning:

Nobody searches using a country's formal ISO name — they type "the PLA", "Beijing", or "NZDF". The countries service maps military-organisation names, capital cities, and common shorthand to ISO3 codes, so a query mentioning any of them still triggers the right inline capability card.

Alternatives considered:
  • Require exact country names or ISO codes to trigger a capability card
  • Use a general-purpose named-entity-recognition model

Explicit per-field confidence labels on country data instead of presenting every figure with equal certainty

Reasoning:

Alliance membership is public record; reported military personnel figures are closer to an estimate. Every field on a country card carries a confirmed, likely, estimated, or unknown label so a chart doesn't get mistaken for ground truth it isn't.

Alternatives considered:
  • Present all fields uniformly with no confidence indicator

A local model for result summarization instead of a cloud LLM API

Reasoning:

The whole point of running this locally is that a search query and what it turns up shouldn't have to leave the machine. Streaming a summary from a small on-device model (llama3.2:1b via Ollama) keeps that guarantee intact even for the one AI feature in the stack, at the cost of a less capable model than a cloud API would offer.

Alternatives considered:
  • Send top result snippets to a cloud LLM API for a higher-quality summary

Tech Stack

  • Docker Compose (8-service stack)
  • Meilisearch (hybrid full-text + vector search)
  • Kiwix (offline ZIM/Wikipedia mirror)
  • SearXNG (privacy-respecting meta-search)
  • FastAPI + SQLite (countries capability API)
  • Ollama / llama3.2:1b (local result summarization)
  • Python (watchdog-based document ingest daemon)
  • nginx (frontend + API proxy)

Result & Impact

In daily use, one query returns local documents, offline-wiki hits, and live web results side by side, filterable by source; a mentioned country surfaces its capability card automatically; and a local model reads back a short summary of the top hits before any of them are opened individually. Dropping a new document into the inbox folder makes it searchable within seconds with no manual re-indexing step. It runs entirely on hardware already owned, with no account, no telemetry, and no functional difference between the wifi being on or off — visible below in a real query ("Type 62 light tank maximum speed") pulling an AI overview and offline-wiki hits, with the underlying Kiwix-served Wikipedia article open behind it.

Learnings

  • A curated keyword allowlist beats indexing everything for a niche research focus — signal-to-noise matters more than coverage when most of the coverage is irrelevant
  • Explicit confidence labeling on aggregated data is worth the extra schema complexity — it's the difference between a chart that informs and one that quietly misleads
  • Keeping the one AI feature fully local was worth the capability tradeoff of a 1B-parameter model over a cloud API, because it's the only way the "no query leaves the machine" guarantee actually holds
