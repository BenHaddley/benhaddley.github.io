HexenVR

Creator · 2026 · 5 min read

A multiplayer VRChat conversion of Hexen's Winnowing Hall dungeon, rebuilt in Unity with UdonSharp — complete with a synced mission state machine, a full class-and-weapon system, and a headless editor pipeline that verifies level completability without opening Play mode.

Overview

HexenVR takes Hexen's Winnowing Hall — the opening dungeon of Raven Software's 1995 dark-fantasy shooter — and rebuilds it as a co-op multiplayer world in VRChat. Players choose a Fighter, Cleric, or Mage, fight through an AI-populated dungeon converted from the original level data, and push through a scripted key-and-gate mission chain toward a boss encounter, with a full campaign chain planned across four maps.

Problem

VRChat's Udon scripting sandbox is built for small interactive rooms, not a dungeon crawler with dozens of networked AI enemies, a class system, and a scripted mission chain — and Hexen's original level, monster, and item placements only exist as raw WAD data, not a Unity scene. The goal was to convert the source game faithfully — real coordinates, real monster placement, real itemization — into a multiplayer world that actually holds together under VRChat's networking limits.

Constraints

  • UdonSharp — VRChat's sandboxed scripting layer — has no free threading, strict networking rules (an object can't mix VRC Object Sync with a manually-synced Udon Behaviour), and no per-player avatar swapping
  • The source level only exists as WAD sector/thing/linedef data — monster placement, item spots, and door geometry all had to be converted from that format, not eyeballed
  • Editor tooling had to be idempotent: the level was rebuilt through dozens of iterative passes, so re-running a build step could never corrupt or duplicate prior work
  • Most of the level graph (NavMesh reachability, door clearance, mission completability) couldn't be verified without an expensive live playtest in ClientSim

Approach

Built an idempotent, menu-driven editor pipeline in Unity that assembles the level stage-by-stage from converted WAD data, using a proven coordinate-conversion formula to place enemies, items, and doors exactly where the original game did. To avoid burning playtests on debugging, a set of headless diagnostic tools walks the same NavMesh and door-collider graph Unity uses at runtime from the command line (-batchmode), reporting exactly which geometry blocks a route before ever pressing Play. Combat, AI, and itemization were ported from the original game's C source into networked UdonSharp behaviours, engineered around VRChat's sync constraints rather than fighting them.

Key Decisions

Headless NavMesh and door-passage verification instead of playtest-only debugging

Reasoning:

A live ClientSim playtest can tell you a boss room 'feels unreachable' but not why. A batchmode diagnostic that walks the same door-collider and NavMesh graph the runtime uses turned that into an exact answer — a specific named door slab blocking a specific threshold — in minutes instead of a debugging session.

Alternatives considered:
  • Rely on manual playtesting and visual inspection alone

Owner-broadcast synced position instead of VRC Object Sync for enemies

Reasoning:

VRChat's build validator hard-rejects an object that carries both Object Sync and a manually-synced Udon Behaviour on the same GameObject. Rather than restructure how enemy AI worked, enemies broadcast their own synced position at low frequency with client-side interpolation instead.

Alternatives considered:
  • Keep Object Sync and drop the custom networked AI
  • Split enemies across two GameObjects to sidestep the conflict

A rideable lift instead of reshaping the boss-room floor

Reasoning:

The raised boss-room floor turned out to be part of one shared mesh spanning the entire map's geometry, so lowering it would have dragged the whole dungeon floor down with it. A lift preserved the original level's geometry exactly and stayed true to Hexen's own design vocabulary of moving platforms.

Alternatives considered:
  • Cut and rebuild the shared floor mesh
  • Add a staircase or ramp

Authored, preplaced monsters instead of spawner waves

Reasoning:

An early version spawned enemies in scripted waves, but that doesn't match how the source level was actually designed. Switching to enemies preplaced at their real WAD monster spots — snapped to the navmesh, typed per-archetype, gated by the original skill flags — made the difficulty curve and pacing authentic to the source map instead of arbitrary.

Alternatives considered:
  • Keep wave-based spawning

Tech Stack

  • Unity 2022.3
  • C# / UdonSharp
  • VRChat SDK3
  • NavMesh AI
  • Unity Editor Scripting & Automation
  • Python (WAD data extraction)

Result & Impact

MAP01 (Winnowing Hall) shipped as a full playable loop — hub, class selection, a 12-weapon arsenal, an authentic bestiary, and a scripted mission chain — verified completable end-to-end by a headless diagnostic pipeline before a single live playtest, and is live on VRChat today.

Learnings

  • A platform sandbox like Udon tends to reject specific combinations of features, not features themselves — hitting 'Object Sync cannot share an object with a manually synced Udon Behaviour' at build time was worth designing around from the start, not patching after the fact
  • Headless verification catches a class of bug playtesting alone misses entirely, especially once a level has hundreds of interactive objects — a door that visually opens but leaves collision behind is invisible until someone specifically tries to walk through it
  • Converting the source format's real coordinate and placement data mathematically beats eyeballing a layout by hand — it's exact, and it survives a level being iterated on dozens of times

Level Conversion Pipeline

Hexen’s WAD sector, thing, and linedef data is exported to JSON via a small offline extraction script, then converted into Unity world space with a coordinate formula validated against the original map: Unity = mapOrigin + (WAD.x / 32, WAD.y / 32). Editor menu commands consume that JSON to place enemies, items, doors, and sky geometry — each command is idempotent, so re-running a step during iteration only ever repairs or extends the scene, never duplicates it.

Networked Combat & Progression

A synced GameManager drives the mission as an explicit state machine (find key → unlock gate → boss fight → escape), gated by a synced progress-flag bitmask so late-joining players catch up to the correct world state automatically. Enemy AI, itemization, and the class system were all ported from the original game’s C source into UdonSharp, restructured around VRChat’s networking model rather than a straight one-to-one port.
