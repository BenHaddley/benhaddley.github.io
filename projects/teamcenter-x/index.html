Teamcenter X

Creator · 2026 · 6 min read

A ground-up local recreation of Siemens Teamcenter X's core PLM data model and workflow engine — Item/Revision/BOM/Dataset/Change Management rebuilt from role-gated first principles, reverse-engineered entirely from public UI screenshots rather than any access to Siemens' real source or documentation.

Overview

Teamcenter X is Siemens' cloud PLM (Product Lifecycle Management) platform — the system engineering orgs use to track parts, assemblies, CAD files, bills of materials, and the approval workflows that move a design from "in work" to "released." This project recreates its core mechanics locally: a Node/Express + SQLite backend modeling Items, Revisions, Datasets, BOM structures, workflows, and formal change requests, fronted by a vanilla-JS SPA styled to match the real Active Workspace client.

The home dashboard after logging in as a Designer — active tasks, changes awaiting review, and recently touched objects, styled to match the real Active Workspace client.

Problem

Real Teamcenter's internal architecture, data model, and source are not public — Siemens sells access to the product, not documentation of how it's built. Recreating even its core mechanics meant starting from zero authoritative information: no schema to copy, no API spec to implement against, nothing but the same interface a paying customer sees in a browser. The actual engineering problem was reverse-engineering a real enterprise system's domain model and UX from observation alone, then implementing something structurally faithful to it rather than a superficial visual clone.

Constraints

  • No access to Siemens' real source, database schema, or internal API — only public marketing pages, blog posts, and third-party walkthroughs of the UI
  • Domain concepts (Item vs. Item Revision, BOM View Revision, Relations, Revision Rules) had to be inferred correctly from a live Teamcenter session and admin documentation, not guessed
  • Needed to run anywhere with zero native dependencies — no system packages, no build toolchain, just a modern Node runtime
  • Business invariants (released structures are immutable, lifecycle transitions are role-gated, mutations are audited) had to be enforced correctly, not just modeled as flat CRUD

Every session starts here — the seeded accounts (Designer, Engineer, Manager, Administrator) are what the role-gated invariants below actually get checked against.

Approach

Domain research came first: a single live Teamcenter session (Revision Rule set to "Latest Working") was used to trace a real Item/Revision/BOM relationship end-to-end, cross-checked against Siemens admin documentation and 40 collected UI reference screenshots covering search, item pages, property grids, BOM trees, and the inbox/workflow views. That domain model was then mapped explicitly to a SQLite schema (items/item_revisions, datasets/dataset_files, bom_lines, workflow templates/instances/tasks, changes/change_items, audit_events), and an Express REST API was built on top with role-gated mutations (Viewer/Designer/Engineer/Manager/Administrator) enforcing the same invariants the real product does — released BOMs are immutable, workflow submission moves a revision from In Work to In Review automatically, only Managers can approve a Change. The frontend is a dependency-free vanilla-JS SPA deliberately kept structurally close to the real Active Workspace shape observed in the reference screenshots.

The Explorer view — real search results across Items, Assemblies, Parts and Documents, each with its own revision, release status, and owner, exactly the shape a live Teamcenter search returns.

Key Decisions

Node's built-in `node:sqlite` instead of a native SQLite driver

Reasoning:

The project needed to run anywhere with a modern Node install and zero native compilation — no native bindings, no build toolchain assumption. The built-in module made `npm install` the only setup step, which matters more for a learning project meant to be picked up and run than for raw query performance.

Alternatives considered:
  • `better-sqlite3` (native bindings, faster but adds a compiled dependency)
  • Postgres (correct long-term choice for multi-user PLM, overkill for a single-user learning scope)

Model real Teamcenter concepts (Item/Revision/BOM/Change) instead of a generic CRUD schema

Reasoning:

A generic "objects with properties" schema would have been faster to build but would have thrown away the actual point of the exercise — understanding why Teamcenter separates an Item's persistent identity from its Revisions, why BOM lines reference Revisions rather than Items, and why Change Management exists as its own object graph rather than just an edit log. Mapping the schema 1:1 to the real domain model forced getting those relationships right.

Alternatives considered:
  • A flat, generic object/property store with type tags
  • Skipping BOM/Change modeling and only implementing Item/Revision/Dataset

An Item Revision detail page — Revision B of the Gearmotor assembly, "In Review", with its actual CAD dataset (a real .glb, 10,168 triangles) loaded in the 3D viewer.

Immutable audit events and a private, randomized-name file vault instead of direct static file serving

Reasoning:

Real PLM systems exist specifically to provide traceability and controlled access to engineering data — serving uploaded files straight out of a public static directory, or skipping an audit trail, would have missed the actual point of the domain. Every mutation writes an audit_events row with before/after state, and dataset files live outside the public directory under randomized names, downloadable only through authenticated, permission-checked endpoints.

Alternatives considered:
  • Serve uploaded files directly from a public uploads directory
  • Skip audit logging as out of scope for a learning project

The dataset vault in practice — every version keeps its own file size and SHA-256 hash, downloadable only through the authenticated API, never served from a public directory.

Tech Stack

  • Node.js (built-in node:sqlite, WAL mode)
  • Express 4 (REST API + static SPA hosting)
  • Vanilla HTML/CSS/JS (no build step)
  • SHA-256 content hashing + salted scrypt password storage
  • Role-based access control
  • Node's built-in test runner (node --test)

Result & Impact

As of the most recent milestone, the persistent, functional slice covers real multi-role workflows end-to-end: authenticated Item/Revision creation and search, BOM line mutations with released-structure protection, a full dataset file vault with versioning and deduplication by content hash, and a working Problem Report → Change Request → Change Notice lifecycle with role-gated approval. Twelve HTTP integration tests exercise authorization, lifecycle protection, and multi-role workflow paths against a real (temporary) SQLite database. A handful of screens — requirements traceability, schedule/Gantt views, dashboard metrics — currently demonstrate layout only, with browser-local state that resets on refresh; the roadmap tracks turning those into persistent features next.

Change impact analysis — a real Change Request, its affected assembly, and the calculated structure impact, the Problem Report → Change Request → Change Notice lifecycle the case study describes.

Learnings

  • Reverse-engineering a real system's domain model from screenshots alone forces genuine understanding of why a data model is shaped the way it is — you can't copy a schema you can't see, so you have to derive it from behavior
  • Distinguishing "visual prototype" screens from "functional and persistent" ones explicitly, in writing, kept scope honest as the project grew — it's easy to let a good-looking mock quietly stand in for a real feature
  • Encoding business invariants as enforced API behavior, not just UI restrictions, is what actually makes something feel like a PLM system rather than a form builder

Domain Research Before Code

Before writing any schema, a live Teamcenter session was used to trace one real object graph end-to-end: an assembly Item and its child part, linked by a single BOM line, both still “In Work” under a “Latest Working” revision rule. That one worked example — cross-referenced against Siemens’ own admin documentation and a 40-image collection of Active Workspace UI screenshots gathered from public blog posts and third-party walkthroughs — became the reference the entire data model and UI were built against, replacing guesswork with an actual (if narrow) ground truth.

Enforcing PLM Invariants as API Behavior

The architecture docs list the invariants the API enforces as non-negotiable, not aspirational: released BOM structures can’t be mutated (a new working revision must be created first), starting a workflow automatically moves a revision from In Work to In Review, only a Manager role can approve, reject, or implement a Change, and every mutating endpoint writes an audit event with before/after state. Building these as server-enforced rules — checked on every request, not just hidden in the UI — is what separates a real PLM recreation from a UI skin over a generic database.
