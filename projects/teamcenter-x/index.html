Teamcenter X

Creator · 2026 · 9 min read

A ground-up local recreation of Siemens Teamcenter X's PLM platform — grown from core Item/Revision/BOM/Dataset/Change Management into a fuller enterprise suite covering requirements traceability, quality/FMEA/compliance, manufacturing (MBOM) and product costing/suppliers, enterprise IAM with object-level ACLs, and an in-browser 3D CAD viewer — all reverse-engineered from public UI screenshots rather than any access to Siemens' real source or documentation.

Overview

Teamcenter X is Siemens' cloud PLM (Product Lifecycle Management) platform — the system engineering orgs use to track parts, assemblies, CAD files, bills of materials, and the approval workflows that move a design from "in work" to "released." This project recreates its mechanics locally: a Node/Express + SQLite backend modeling Items, Revisions, Datasets, BOM structures, workflows, formal change requests, requirements traceability, quality/FMEA/compliance, manufacturing process plans, and product costing/suppliers, fronted by a vanilla-JS SPA styled to match the real Active Workspace client — including a Three.js viewer that renders real GLB/glTF CAD datasets in-browser, with local STL-to-GLB conversion for formats that aren't natively viewable.

Problem

Real Teamcenter's internal architecture, data model, and source are not public — Siemens sells access to the product, not documentation of how it's built. Recreating even its core mechanics meant starting from zero authoritative information: no schema to copy, no API spec to implement against, nothing but the same interface a paying customer sees in a browser. The actual engineering problem was reverse-engineering a real enterprise system's domain model and UX from observation alone, then implementing something structurally faithful to it rather than a superficial visual clone.

Constraints

  • No access to Siemens' real source, database schema, or internal API — only public marketing pages, blog posts, and third-party walkthroughs of the UI
  • Domain concepts (Item vs. Item Revision, BOM View Revision, Relations, Revision Rules) had to be inferred correctly from a live Teamcenter session and admin documentation, not guessed
  • Needed to run anywhere with zero native dependencies — no system packages, no build toolchain, just a modern Node runtime
  • Business invariants (released structures are immutable, lifecycle transitions are role-gated, mutations are audited) had to be enforced correctly, not just modeled as flat CRUD

Approach

Domain research came first: a single live Teamcenter session (Revision Rule set to "Latest Working") was used to trace a real Item/Revision/BOM relationship end-to-end, cross-checked against Siemens admin documentation and 40 collected UI reference screenshots covering search, item pages, property grids, BOM trees, and the inbox/workflow views. That domain model was then mapped explicitly to a SQLite schema (items/item_revisions, datasets/dataset_files, bom_lines, workflow templates/instances/tasks, changes/change_items, audit_events), and an Express REST API was built on top with role-gated mutations (Viewer/Designer/Engineer/Manager/Administrator) enforcing the same invariants the real product does — released BOMs are immutable, workflow submission moves a revision from In Work to In Review automatically, only Managers can approve a Change. The frontend is a dependency-free vanilla-JS SPA deliberately kept structurally close to the real Active Workspace shape observed in the reference screenshots.

Key Decisions

Node's built-in `node:sqlite` instead of a native SQLite driver

Reasoning:

The project needed to run anywhere with a modern Node install and zero native compilation — no native bindings, no build toolchain assumption. The built-in module made `npm install` the only setup step, which matters more for a learning project meant to be picked up and run than for raw query performance.

Alternatives considered:
  • `better-sqlite3` (native bindings, faster but adds a compiled dependency)
  • Postgres (correct long-term choice for multi-user PLM, overkill for a single-user learning scope)

Model real Teamcenter concepts (Item/Revision/BOM/Change) instead of a generic CRUD schema

Reasoning:

A generic "objects with properties" schema would have been faster to build but would have thrown away the actual point of the exercise — understanding why Teamcenter separates an Item's persistent identity from its Revisions, why BOM lines reference Revisions rather than Items, and why Change Management exists as its own object graph rather than just an edit log. Mapping the schema 1:1 to the real domain model forced getting those relationships right.

Alternatives considered:
  • A flat, generic object/property store with type tags
  • Skipping BOM/Change modeling and only implementing Item/Revision/Dataset

Immutable audit events and a private, randomized-name file vault instead of direct static file serving

Reasoning:

Real PLM systems exist specifically to provide traceability and controlled access to engineering data — serving uploaded files straight out of a public static directory, or skipping an audit trail, would have missed the actual point of the domain. Every mutation writes an audit_events row with before/after state, and dataset files live outside the public directory under randomized names, downloadable only through authenticated, permission-checked endpoints.

Alternatives considered:
  • Serve uploaded files directly from a public uploads directory
  • Skip audit logging as out of scope for a learning project

Local STL-to-GLB conversion with a content-hashed, validated derivative cache instead of requiring pre-converted uploads

Reasoning:

Real Dataset files aren't all natively browser-viewable — STL has no color/scene graph and no WebGL loader path the way glTF/GLB does. Rather than push that conversion problem onto the user (upload a GLB or don't view it), the server converts STL to GLB locally via Three.js's STL loader and gltf-transform, caches the result under a key derived from the source file's own content hash plus the converter's identity/version, and validates the output GLB's binary header before ever serving it. The source Dataset file stays authoritative and keeps its own ACL; the derivative is never treated as a separate, less-protected copy.

Alternatives considered:
  • Require users to upload pre-converted GLB/glTF files and leave other CAD formats unsupported
  • Convert on every request instead of caching validated derivatives

Tech Stack

  • Node.js (built-in node:sqlite, WAL mode)
  • Express 4 (REST API + static SPA hosting)
  • Vanilla HTML/CSS/JS (no build step)
  • Three.js (GLB/glTF 3D CAD viewer)
  • @gltf-transform/core (local STL→GLB conversion)
  • SHA-256 content hashing + salted scrypt password storage
  • Role-based access control + object-level ACLs
  • Node's built-in test runner (node --test)

Result & Impact

The persistent, functional slice now covers real multi-role workflows end-to-end across a much wider PLM surface than the original core slice: authenticated Item/Revision creation and search, BOM line mutations with released-structure protection, a full dataset file vault with versioning and deduplication by content hash, a Problem Report → Change Request → Change Notice lifecycle with role-gated approval, requirements traceability with frozen baselines and verification coverage, Quality/FMEA/Compliance records with real lifecycles and RPN calculation, manufacturing MBOM/process plans with EBOM comparison, and product costing/supplier management with quote-based cost roll-ups. Enterprise IAM adds persistent users, groups, and object-level ACLs on top of the original role hierarchy. A Three.js viewer renders real GLB/glTF CAD datasets in-browser, with local STL-to-GLB conversion for formats that aren't natively viewable. Fifty-two HTTP integration tests now exercise all of the above against a real (temporary) SQLite database — up from twelve at the original milestone. Only dashboard summary metrics remain browser-local/visual-only at this point; requirements, schedule/Gantt, and the Task Board — prototype-only before — are now persistent, real features.

Learnings

  • Reverse-engineering a real system's domain model from screenshots alone forces genuine understanding of why a data model is shaped the way it is — you can't copy a schema you can't see, so you have to derive it from behavior
  • Distinguishing "visual prototype" screens from "functional and persistent" ones explicitly, in writing, kept scope honest as the project grew — it's easy to let a good-looking mock quietly stand in for a real feature, and that discipline is what let prototype screens actually graduate to real ones later instead of staying permanently fake
  • Encoding business invariants as enforced API behavior, not just UI restrictions, is what actually makes something feel like a PLM system rather than a form builder
  • A generalized polymorphic link model (built once for Requirements traceability) turned out to be reusable, unmodified, as the backbone for Change, Quality, FMEA, and Compliance relationships too — getting one cross-cutting pattern right early paid off across every domain added after it

Domain Research Before Code

Before writing any schema, a live Teamcenter session was used to trace one real object graph end-to-end: an assembly Item and its child part, linked by a single BOM line, both still “In Work” under a “Latest Working” revision rule. That one worked example — cross-referenced against Siemens’ own admin documentation and a 40-image collection of Active Workspace UI screenshots gathered from public blog posts and third-party walkthroughs — became the reference the entire data model and UI were built against, replacing guesswork with an actual (if narrow) ground truth.

Enforcing PLM Invariants as API Behavior

The architecture docs list the invariants the API enforces as non-negotiable, not aspirational: released BOM structures can’t be mutated (a new working revision must be created first), starting a workflow automatically moves a revision from In Work to In Review, only a Manager role can approve, reject, or implement a Change, and every mutating endpoint writes an audit event with before/after state. Building these as server-enforced rules — checked on every request, not just hidden in the UI — is what separates a real PLM recreation from a UI skin over a generic database.

Growing From Core PLM Into a Fuller Enterprise Suite

The original milestone covered Item/Revision/BOM/Dataset/Change Management — the load-bearing core of any PLM system. Since then the same schema-first, invariant-enforced approach has been extended across most of the rest of a real PLM platform’s domain: requirements traceability with frozen baselines and verification coverage rollups; Quality, FMEA, and Compliance records with real state machines (not free-text status fields) and server-computed RPN scoring; manufacturing MBOM and process plans that compare against the design EBOM instead of drifting independently from it; and product costing with supplier/quote management, where the server refuses to silently guess a price when more than one valid quote exists. Enterprise IAM was generalized at the same time — persistent users, groups, and object-level ACLs that can override the normal role gate and produce a real 403, reused by every domain through one centralized hasObjectAccess check rather than being bolted onto each feature separately.

Rendering Real CAD Data Without a Native Viewer

Teamcenter’s whole reason for existing is managing engineering data, so a Dataset file vault that can’t actually show you the CAD model is only doing half the job. The viewer renders GLB and glTF files directly in the browser with Three.js — orbit, pan, zoom, fit-to-view, a grid toggle, and model metadata alongside the 3D view. STL files, which have no scene graph or color information and no native WebGL loader path, get converted locally to GLB through @gltf-transform/core, with the derivative cached under a key derived from the source file’s own content hash so the same file never gets reconverted, and the output validated at the binary level (correct glTF magic bytes, version, and length header) before it’s ever served. The source Dataset file stays authoritative throughout — the GLB is a derivative, not a replacement, and it inherits the source file’s own access control rather than becoming an unprotected side channel to the same data.
