SCPDOOM (MalO SAO)

Creator · 2026 · 5 min read

A WAD-derived raycaster shooter built for a hacker-con badge — real Doom assets, maps, and enemies converted from a DOOM1.wad file into a compact engine that runs on a 128×128 4-bit-grayscale OLED with buzzer-only audio.

Overview

SCPDOOM is a lightweight raycaster game built for the MalO SAO — an open-source "Simple Add-On" badge (RP2350B, 16 MB flash, 128×128 SSD1327 OLED) designed by ParallelLogic and distributed at DEFCON 34. The hardware and base firmware are the open-source MalO platform; SCPDOOM is the original addition layered on top of it — a Main → Games → scpdoom menu entry that converts a real DOOM1.wad into grayscale wall/floor/monster/item/weapon assets, compact per-level maps, and buzzer sound effects, then renders them through a from-scratch raycasting engine running on the badge's microcontroller.

Problem

A real Doom source port is far too heavy for an add-on badge — no GPU, a 128×128 4-bit grayscale panel, single-touch capacitive input, and a piezo buzzer instead of a sound chip. But shipping a generic "inspired by Doom" game would have thrown away what makes the source material worth using at all: its actual level geometry, monster placement, and weapon roster. The goal was a raycaster that stayed faithful to real WAD data while fitting inside the badge's real constraints.

Constraints

  • Display is 128×128 px at 4-bit grayscale (16 levels) via an LVGL L8 canvas — no color, no texture filtering budget for a full renderer
  • Audio path is a single piezo buzzer on a GPIO pin (PWM tone approximation only) — no sample playback, no music, SFX only
  • Input is single-touch capacitive controls, not a D-pad or analog stick, so movement/turn/strafe/fire/weapon-cycle all had to map onto a small discrete control set
  • Flash is 16 MB shared across the whole MalO firmware image, so WAD-derived assets, maps, and audio all had to be preprocessed and compacted offline rather than parsed from a live WAD at runtime
  • The original working source tree was lost mid-development, so the current tree is a reconstruction rebuilt from upstream MalO plus the recorded scpdoom implementation

Approach

Three offline Python generators read a real DOOM1.wad and emit static C headers containing pre-converted grayscale sprites, compact grid maps, and buzzer envelope/tone tables baked in at build time. The runtime side is a "safe raycaster" — not a full Doom engine port — that walks those baked assets and maps to render walls, sprites, and a Doom-style HUD (status face, health/armor/ammo, keys, powerups) with an automap overlay, while running enemy AI, projectiles, pickups, and hazard tiles as simplified compact state machines sized for the hardware.

Key Decisions

Offline WAD-to-header asset baking instead of runtime WAD parsing

Reasoning:

Parsing WAD lumps live on an RP2350B would burn flash I/O and RAM the badge doesn't have to spare, and the asset set only needs to be built once per WAD. Baking assets, maps, and audio into static headers at build time turns a runtime parsing problem into a one-time offline conversion, keeping the firmware itself simple and fast.

Alternatives considered:
  • Parse and decode WAD lumps on-device at boot or on level load
  • Ship a smaller hand-authored asset set instead of deriving it from the real WAD

A hand-authored E1M1 layout instead of a purely mechanical WAD-to-grid conversion

Reasoning:

Other levels are compact WAD-derived grids, but E1M1 — the level most players would recognize — was specifically authored as a compact Hangar-inspired layout rather than a raw mechanical downsample, because a literal grid conversion of the source geometry didn't read well at this resolution and control scheme.

Alternatives considered:
  • Apply the same mechanical grid-conversion process uniformly across all levels

A "safe raycaster" scoped explicitly below a full Doom port

Reasoning:

This is documented as a compact raycaster with approximate tagged doors/switches and simplified monster AI/item balance, not a full engine port — an honest, scoped target that fits real-time rendering, enemy logic, and physics into the RP2350B's budget instead of chasing full engine fidelity that the hardware can't sustain.

Alternatives considered:
  • Attempt a fuller Doom engine port and accept degraded frame rate/behavior

Tech Stack

  • C/C++ (Arduino framework, RP2350B target)
  • LVGL (grayscale canvas rendering)
  • Custom raycasting engine
  • Python (WAD parsing/asset, map, and audio generation tooling)
  • PWM buzzer audio synthesis
  • Arduino CLI build tooling

Result & Impact

SCPDOOM shipped as a real, playable game on physical hardware distributed at a DEFCON 34 badge drop — a full menu-integrated raycaster with nine WAD-derived levels, four weapons, a real enemy and pickup roster, hazard tiles, an automap, and a Doom-style HUD, running entirely on a badge built for LED blinkies and mini-games. The offline generator pipeline also means regenerating the entire asset/map/audio set from a different WAD is a three-script rerun, not a rewrite.

Learnings

  • Scoping honestly to "a raycaster inspired by real WAD data" instead of "a Doom port" kept the project achievable — naming the actual constraint up front is more useful than quietly under-delivering against an implied full-port promise
  • Baking derived content into static headers at build time is a good general pattern for embedded targets: it moves expensive parsing off the device and turns "regenerate content" into a scripted, repeatable step
  • Recovering a lost working tree from documentation and recorded implementation details is only possible if the design decisions and file layout were written down somewhere outside the ephemeral session

Built on Open Hardware, Not From Scratch

The MalO SAO board itself — RP2350B, 16 MB flash, SSD1327 OLED, IMU, IR transceiver, hall-effect and light sensors, RFID, and the base firmware menu system — is ParallelLogic’s open-source “Simple Add-On” design (CC BY-SA 3.0), sold and distributed at DEFCON 34, with PCB artwork by HotGlewd and pixel art by BitAssembly. SCPDOOM is a from-scratch game built as an addition to that platform, not a hardware or base-firmware design credit.
