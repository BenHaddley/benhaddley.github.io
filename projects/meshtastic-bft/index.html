Meshtastic Blue Force Tracking

Contributor — Software & Documentation · 2025 · 7 min read

A secure, real-time friendly-force tracking system built on civilian Meshtastic LoRa mesh radios instead of military-specified equipment — cutting the cost per tracked soldier from roughly NZ$100,000 to NZ$140, and winning the 2025 New Zealand Defence Force Innovation of the Year award.

Read the NZDF story ↗

Overview

Blue Force Tracking (BFT) is an NZDF project developed within 2nd Signal Squadron, giving commanders a live map of friendly-force positions by repurposing Meshtastic — an open-source LoRa mesh radio protocol — instead of relying on manual voice reporting or specialist military tracking radios. I contributed the fleet-provisioning software and the technical documentation, working alongside others on the wider system: each soldier or vehicle carries a small GPS-equipped LoRa node, and nodes relay each other's position and status over an encrypted mesh with no cellular network or SIM required, feeding a live picture through to command systems like SitaWare.

Problem

The standing method for tracking friendly-force locations is manual reporting — Location Status Reports (LOCSTATs) called in over voice radio. That means delayed and inaccurate positions, radio channels congested with routine position traffic, total reliance on someone remembering to report in, and no live tracking at all in denied, intermittent, or limited (DIL) communications environments. All of that reduces situational awareness, slows decisions, and adds to the command-and-control burden — and the standard alternative, specialist tracking radios like the Harris 160G, costs roughly NZ$33,000–100,000 per unit, which puts fleet-wide tracking out of reach.

Constraints

  • Had to be affordable enough to issue at scale — to every soldier, not just vehicle commanders — which ruled out anything priced like a specialist military radio
  • Had to work with no cellular network or SIM, since DIL environments and exercise areas can't assume commercial coverage
  • Location data has to be encrypted end-to-end so an adversary intercepting mesh traffic can't extract or spoof friendly positions
  • Setup and operation needed to be fast enough for a rifleman to use, not a signals specialist doing a crypto fill — the Harris comparison point is specialist programming plus crypto fills versus minutes per node
  • Had to interoperate with existing command systems (SitaWare) rather than becoming a standalone tracker nobody at the command post actually sees

Approach

The system runs on Meshtastic firmware over LoRa radios (LILYGO T-Echo hardware) with built-in GPS, operating in NZ's unlicensed short-range device band so no radio license or carrier is needed. Nodes relay each other's encrypted position and status over the mesh, extending range well past any single radio's line of sight, and feed into SitaWare as live tracks so commanders see the same picture they already use for command and control. My contribution was making fleet-wide deployment realistic: a small desktop provisioning tool that wraps the official `meshtastic` CLI, auto-detecting connected nodes over serial and applying a full device configuration — LoRa region and TX power, channel PSK, GPS broadcast interval, power/battery profile, device role, and identity — from tabbed forms instead of hand-typing CLI flags per node, one at a time, for every radio in a fleet. I also wrote the technical documentation covering setup, configuration, and field use.

Key Decisions

Civilian Meshtastic hardware instead of a military-specified tracking radio

Reasoning:

A Harris 160G costs roughly NZ$33,000–100,000 per unit and needs specialist programming and crypto fills to stand up — fine for a handful of vehicle commanders, unworkable for tracking every soldier. A NZ$140 LoRa node with built-in GPS, configured over a phone or laptop in minutes, makes fleet-wide issue actually affordable — and in field testing it returned more accurate GPS data than expected, not just a cheaper compromise.

Alternatives considered:
  • Continue relying on manual LOCSTAT voice reporting
  • Issue military tracking radios only to vehicle/section commanders rather than every soldier

Build a dedicated provisioning tool instead of configuring each node by hand through the phone app

Reasoning:

The standard Meshtastic phone-app workflow (5–10 minutes per node) is fine for a handful of radios, but a real deployment means dozens of nodes that all need the same region, channel PSK, GPS interval, and power profile applied consistently — doing that by hand invites drift between nodes and eats a disproportionate amount of setup time at scale. A tabbed desktop tool that applies the full configuration in one pass, and auto-detects which serial port a node is even on, turns fleet provisioning into a repeatable procedure instead of dozens of manual phone sessions.

Alternatives considered:
  • Configure every node individually through the official phone app
  • Write a config file and a one-shot CLI script with no UI, accepting that non-specialists would need to edit it directly

Scan all candidate serial ports concurrently instead of one at a time

Reasoning:

Detecting which of several `/dev/ttyACM*`/`/dev/ttyUSB*` devices is actually a Meshtastic node means running a `meshtastic --info` probe against each candidate, which takes a few seconds per port. Firing one probe thread per candidate and joining them all cuts detection time to roughly the length of the slowest single probe instead of the sum of all of them, which matters when you're plugging in and provisioning several radios back-to-back.

Alternatives considered:
  • Probe each candidate serial port sequentially
  • Require the operator to manually type in the correct serial port

Run every meshtastic CLI call on a background thread instead of the Tkinter main loop

Reasoning:

Every configuration change shells out to the `meshtastic` CLI, which can take several seconds — including a deliberate delay after an identity change, since renaming a node triggers a reboot. Running those calls inline would freeze the UI for the duration; running them on daemon threads and marshalling results back with `self.after()` keeps the log and status bar live and responsive while a multi-step provisioning sequence runs in the background.

Alternatives considered:
  • Run CLI calls synchronously and accept a frozen UI during provisioning

Tech Stack

  • Meshtastic (open-source LoRa mesh firmware)
  • LoRa radio hardware (LILYGO T-Echo, integrated GPS)
  • AES-256 encryption (mesh transport security)
  • Python (Tkinter provisioning GUI)
  • Python threading (concurrent port scan + background CLI execution)
  • meshtastic CLI (device configuration)
  • SitaWare / ATAK (Cursor-on-Target position feed)

Result & Impact

Field-tested over an 8-hour trial in central Wellington on 16 October 2025 — starting from a single node on the Defence House rooftop and scaling to five radios across the city — the mesh stayed connected through heavy urban RF interference and continuously tracked every node, with GPS accuracy that came out ahead of expectations. The approach won the 2025 New Zealand Defence Force Innovation of the Year award, and the proposed next step is a 10-node-plus-homestation-and-repeater pilot with a two-week trial evaluating coverage, update rate, and after-action-review value before wider rollout.

Learnings

  • A civilian, unlicensed-band technology can outperform an expensive purpose-built military radio on the metric that actually matters for adoption — cost per unit issued — without silently compromising the capability it replaces, provided the security model (encryption, controlled access) is deliberately built in rather than assumed
  • Tooling for provisioning at scale is not optional once a proof-of-concept has to become a real fleet: what takes minutes for one device becomes the whole project's bottleneck across dozens, so the provisioning tool ended up being as important to the outcome as the radios themselves
  • Testing in the harshest plausible RF environment (dense urban interference) rather than a clean field gave a far more convincing result than a quiet test would have — the mesh proved itself specifically by surviving the conditions it was skeptically expected to fail in

Provisioning at Fleet Scale

Standing up one Meshtastic node through the official phone app is quick, but standing up a fleet consistently is a different problem. The provisioning tool scans every candidate serial port concurrently to find connected nodes, then exposes the full device configuration — LoRa region and TX power, channel PSK/URL, GPS enable and broadcast interval (with optional fixed coordinates), battery size and charge profile, power-saving mode, device role (client, router, or tracker), and identity — as tabbed forms instead of raw CLI flags. Every change runs on a background thread against the real meshtastic CLI, with deliberate delays built in where the hardware needs them — renaming a node’s identity triggers a device reboot, so the next command in a sequence waits for it rather than racing it.

Why the Cheaper Radio Won

The comparison that mattered wasn’t performance on paper — a Harris 160G’s specialist HF/VHF secure voice and beyond-line-of-sight capability outclasses a text-and-position LoRa node in a lot of ways. It was cost-per-unit-fielded and time-to-deploy: NZ$140 versus tens of thousands of dollars, and minutes of setup versus specialist programming and crypto fills. For the specific problem of live position tracking across a whole formation rather than a handful of vehicles, that tradeoff — plus GPS accuracy that held up in testing — made the civilian option the more capable choice for the job actually being solved, not just the budget one.
