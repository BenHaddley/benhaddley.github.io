Lancer Beyond

Creator · 2026 · 6 min read

An unofficial, browser-based campaign manager, character builder, and 3D virtual tabletop for the Lancer TTRPG, built on a pure-TypeScript rules engine that imports real Lancer Content Packages and enforces every rule on a live hex-grid battlefield.

Overview

Lancer Beyond is a pnpm monorepo that rebuilds the Lancer tabletop RPG — pilot and mech management in the spirit of D&D Beyond, campaign and mission tracking, narrative scene tools, and tactical mech combat — as a single local-first web app. A React Three Fiber tabletop renders a real axial hex grid with full rules enforcement, backed by domain-model, rules-engine, and content-import packages that have no framework dependency at all.

Problem

Lancer's tactical layer is genuinely complex — hex positioning and threat areas, a damage/heat/structure/stress pipeline, licence-gated content across a large ecosystem of official and third-party Lancer Content Packages (LCPs) — and most digital tools for it either flatten that down to a character-sheet spreadsheet with dice macros, or hand-wave the tactical board entirely. Getting a group playing at a real table (not just over voice chat) with all of that enforced correctly, without a game master manually adjudicating every rule, is a different and harder problem than a character builder alone.

Constraints

  • Content compatibility isn't optional: the game's content ecosystem lives in the LCP format, so imported packs (official or third-party) have to import correctly or fail with a clear reason — not silently break the builder
  • No paid rulebook content can ship in the repo, so all game data comes from openly licensed sources or packs the user imports themselves
  • Needed real multiplayer for people sitting at the same physical table, without taking on a hosted backend, authentication, and conflict resolution before the tactical game itself was solid
  • Rules logic has to stay testable and deterministic — dice results can't depend on hidden state that breaks replay or unit tests
  • 3D unit presentation had to work without a model-authoring pipeline in place yet, so combat still needed to read clearly on the board

Approach

The rules-heavy parts of the system — domain types, game data access, the dice/checks/progression/validation engine, hex-grid math, the encounter turn-cycle state machine, and LCP import/validation — are split into standalone, framework-free TypeScript packages consumed by a Next.js 15 app. The web app layers a React Three Fiber tactical board, Dexie/IndexedDB local-first persistence, and a COMP/CON-inspired command-deck UI on top, so every attack, movement, or check the player makes on the board routes through the same rules functions the unit tests exercise directly.

Key Decisions

A "dumb relay" LAN sync server instead of building cloud multiplayer first

Reasoning:

People needed to play together at a real table now, and a full backend (auth, hosted persistence, conflict resolution) was a much bigger project than the tactical game itself. The relay just forwards full-state messages between clients in a room over WebSockets — it holds no game logic and no persistence. All the actual rules about what a message means live client-side in a pure, unit-tested protocol module, with last-write-wins state mirroring and a simple first-device-claims-the-room-key scheme meant to stop accidental drop-ins, not act as real security.

Alternatives considered:
  • Wait for the Phase 7 Supabase cloud foundation (auth, hosted sync, conflict resolution) before shipping any multiplayer
  • Build a stateful authoritative game server instead of a dumb relay

Rules, hex-grid, and content-import logic live in framework-free packages with injectable randomness

Reasoning:

Every rolling function takes a Roller argument instead of calling Math.random() directly, so tests run on fixed dice sequences and games can replay deterministically from a seed. Keeping the rules, hex-grid, and content-import packages free of React, Next.js, or browser APIs meant the actual game logic could be fully unit-tested in isolation from the UI, rather than only reachable through end-to-end browser tests.

Alternatives considered:
  • Implement rules logic inline in React components/hooks
  • Call the platform RNG directly and rely on E2E tests alone for coverage

A real LCP import pipeline instead of a fixed, hand-authored content set

Reasoning:

Lancer's actual content ecosystem is built around the Lancer Content Package format, so a closed set of hardcoded frames and weapons would cut the app off from both official expansions and the wider third-party content scene. The importer unzips a .lcp file and validates every record individually against the same schemas the rest of the app uses, reporting invalid, duplicate, unsupported, or overriding records explicitly instead of silently dropping anything.

Alternatives considered:
  • Hardcode a fixed subset of official content and skip general LCP support

A constrained "Roleplay Experience Epic" instead of open-ended narrative UI

Reasoning:

The tactical engine risked feeling like a spreadsheet with extra steps, but the fix wasn't to add freeform narrative UI on top — it was scoped by an explicit product rule: every narrative feature must either prepare fiction before a rule call, make an existing rule call easier to choose, present a result as a story beat, or record table memory. The rules engine, scene log, and GM rulings stay the sole authority; narrative tooling never bypasses them.

Alternatives considered:
  • Leave narrative play to freeform GM notes outside the app
  • Let narrative features resolve outcomes independently of the rules/encounter engines

Tech Stack

  • TypeScript (pnpm workspaces, 6 packages)
  • Next.js 15 / React
  • React Three Fiber (3D tactical board)
  • Dexie / IndexedDB (local-first persistence)
  • Zod (schema validation for game data and LCP imports)
  • Vitest (unit tests) + Playwright (E2E)
  • WebSockets (LAN table-sync relay)

Result & Impact

As of the last full status update, the local vertical slice — create a pilot, build a mech from imported content, run a full tactical encounter with the complete gameplay and GM-sandbox rule sets, and advance between missions — is complete and passing 543 unit tests and 46 Playwright end-to-end tests, with lint, build, and format gates clean across all six projects. Cloud accounts and Supabase-backed multiplayer are the explicitly deferred next phase; local LAN table sync already lets a group play together today.

Learnings

  • Deferring the hardest infrastructure problem (hosted multiplayer/auth) in favor of a much simpler LAN relay let real multiplayer ship early, without blocking on the eventual cloud phase
  • Keeping rules logic in framework-free packages with injected randomness pays off directly in test quality — deterministic dice sequences and seeded replay aren't retrofittable if the RNG and the UI are tangled together from the start
  • A content-import format from a real, external ecosystem is worth validating record-by-record with explicit reporting rather than best-effort parsing, since silent partial failures are far worse in a rules-heavy game than a loud, specific rejection
  • Constraining a whole feature epic with one product rule kept a large batch of narrative UI work from drifting into a second, competing source of truth

LAN Table Sync

The sync layer is deliberately two pieces: a stateless relay server that only forwards JSON messages by room, and a client-side protocol module of pure functions (peer-list reducers, message shape validation, acceptance rules) that’s unit-tested without ever opening a socket. Full encounter state is mirrored with last-write-wins semantics and a monotonically increasing revision counter per client; presence messages age peers out after 30 seconds of silence. The room “key” is just whatever the first device to join sends — enough to stop an accidental second table from joining the wrong room, explicitly not cryptographic auth.

Hex-Grid Tactical Board

The hex-grid package implements a full axial coordinate system — neighbours, distance, rings, areas, line-drawing, and pointy-top world-space conversion — plus A* pathfinding and reachable-hex computation for movement previews, all independent of the renderer. The board itself renders procedural terrain and imported standee art as billboarded sprites rather than full 3D models, a deliberate choice to ship a readable, fully rules-enforced board ahead of building a full model pipeline.
