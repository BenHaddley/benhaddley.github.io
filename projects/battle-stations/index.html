Battle Stations

Programmer & Systems Designer · 2026 · 2 people · 9 min read

A railway tower-defense prototype rebuilt from scratch in Godot 4, working from a friend's years-old, mostly-lost concept sketches and hand-drawn board art — now with a purpose-built dev tool that lets the artist check his own board designs against the game's real grid without touching a line of code.

Overview

Battle Stations is a railway-themed tower-defense game: you build a train of turret cars that patrols a rail loop, defending a station from waves of spiders. The concept and every piece of art — the board, the units, the character cast that narrates the tutorial — belong to Amiigoose (amiigoose on Discord, @amiigoose on YouTube). This has been his dream game since at least late 2023, when the earliest concept sketches and unit ideas were shared. I'm the programmer: an old Unity prototype had stalled, so I rebuilt the whole thing in Godot 4 against his art and ideas, and I keep building the systems underneath whatever he draws next.

Problem

By the time I picked this back up, there wasn't much left to build from. The original Unity project existed but had stalled, and a lot of the early concept material — most notably a 2023 spreadsheet of unit ideas — had already gone missing (the Google Sheets link now just returns a deleted-file page). What survived was scattered Discord conversation, some recovered art, and Amiigoose's hand-drawn illustrations of the game board itself. That last part was its own specific problem: a drawing is not grid data. Turret spacing, rail-lattice geometry, spider lanes, and the station's 'leak' line all had to be reverse-engineered from an illustration into exact numbers the game could actually run on — and then, every time the art changed, someone had to re-check that the numbers still matched the drawing. Amiigoose has no reason to open Godot or read GDScript, so that check couldn't just live in my head or in a spec doc he'd have to trust blind.

Constraints

  • The original Unity build had stalled, and a chunk of the earliest concept material (a 2023 unit-ideas spreadsheet) was already unrecoverable by the time the Godot rebuild started
  • The source design exists as hand-drawn board illustrations, not grid data — rail spacing and lane positions had to be measured out of a drawing, not authored as numbers from the start
  • The artist needed a way to verify his own board art lines up with the game's real grid without installing Godot or reading code
  • Godot 4's GL Compatibility renderer had to keep a hand-drawn, paper-grain art style legible after a web export, not just inside the desktop editor
  • Four very different turret weapons (single shot, AoE blast, burst fire, splash cannon) needed to share one targeting/patrol/rotation core without collapsing into one giant conditional

Approach

The active project is a from-scratch Godot 4 rebuild of the stalled Unity prototype — the Unity snapshot is kept in the repo under legacy_unity/ purely for provenance. Gameplay state lives in a small set of autoload singletons (CampaignManager, LevelManager, BuildManager, PhaseManager, UIManager, AudioFX) so a level reload only has to reset the state that actually needs to survive between runs. Combat cars share one Turret base class that owns targeting, rail patrol, and the firing timer; each weapon type overrides just the parts that make it different — how it fires, what it fires, and now, what it sounds like. The most direct answer to the art/grid problem is a dedicated 'Artist Grid' build: it renders the exact rail lattice, spider lane centers, and station leak line the code actually uses, drawn directly over Amiigoose's own illustrated board, and it's reachable from a plain URL — no editor, no build step, just a page he can open and look at.

Key Decisions

Build a dedicated Artist Grid view instead of describing the grid to the artist in coordinates

Reasoning:

Amiigoose's board art is the actual design source, but a hand-drawn illustration and a numeric grid can silently drift apart the moment either side changes something. Rather than translate pixel measurements back and forth over Discord and hope the next revision still lined up, I built a build that overlays the game's real lattice — cyan rail centers, pink spider lane centers, an orange station leak line — directly on top of his illustration. He can open it, look, and see immediately whether his drawing and my grid agree, without needing to know what any of the code behind it does.

Alternatives considered:
  • Hand him a written spec of coordinates and trust future art revisions against it
  • Have the programmer manually eyeball-align every new board illustration by hand

One shared Turret base class, with each weapon overriding its own firing behavior

Reasoning:

Four turret types needed to behave nothing alike at the moment they fire — a single aimed shot, a close-range blast that hits everything in an area, a seven-round spread burst, and a slow splash cannon — while sharing identical targeting, rail-patrol, and rotation logic. Giving the base class one shoot() that subclasses override (rather than one shoot() with a type switch inside it) meant adding a new weapon never risks breaking an existing one, and each turret now plays its own distinct sound from that same override point.

Alternatives considered:
  • A single shoot() function with a branch per turret type
  • A fully data-driven weapon config with no code override point for genuinely different behaviors

Migrate to Godot 4 rather than keep pushing on the stalled Unity prototype

Reasoning:

The Unity project existed but wasn't moving. Rebuilding meant porting the recovered gameplay scripts to GDScript and rebuilding the scenes rather than starting design from zero, while gaining a much simpler autoload/singleton model for the shared game state and a browser export path that didn't depend on Unity's own web tooling.

Alternatives considered:
  • Keep iterating on the existing Unity prototype
  • Start over in a different engine entirely

Keep tutorial-completion state in its own save file, separate from campaign progress

Reasoning:

Continuing a saved campaign should skip lessons the player has already seen, but starting a brand-new campaign should always replay the tutorial — even in a browser, where a deleted save might not have flushed to IndexedDB yet by the time the next scene loads. Keeping the tutorial flag in its own file means Restart only has to clear that one file, instead of untangling tutorial state from everything else campaign progress tracks.

Alternatives considered:
  • Store one combined save blob and infer tutorial state from campaign progress
  • Always replay the tutorial on every launch regardless of save state

Tech Stack

  • Godot 4.3 (GDScript, GL Compatibility renderer)
  • Web export for browser play
  • Autoload singletons for shared game state (CampaignManager, LevelManager, BuildManager, PhaseManager, UIManager, AudioFX)
  • Hand-drawn illustration pipeline — board, units, and character art by Amiigoose, paper-grain textures, Architects Daughter type
  • Procedurally synthesized turret gunfire SFX (Python/NumPy-generated WAVs, one distinct sound per weapon)

Learnings

  • A dedicated build that shows a non-programmer collaborator exactly what the code sees is worth more than any written spec — the Artist Grid view turned 'does your drawing match my grid' from a back-and-forth over Discord into something he can just look at
  • Giving each weapon its own override point on a shared base class let four very different firing behaviors coexist without one growing into a conditional that risks the other three
  • Concept material scattered across old Discord messages decays fast — a spreadsheet linked in December 2023 was already a dead link by the time this rebuild needed it, which is exactly why the project now keeps a confidence-labelled wiki instead of trusting memory or chat history

This is Amiigoose’s game, first and foremost — the board, the units, the whole visual identity, and the character cast narrating the tutorial are all his. You can find more of his work at youtube.com/@amiigoose. I’m the one writing the Godot code underneath it.

Starting from what was left

The Unity prototype this replaced had stalled, and by the time I came back to rebuild it, a fair amount of the earliest concept work was already gone — most notably a 2023 spreadsheet of unit ideas that’s now just a “file deleted” page on Google’s end. What did survive was scattered Discord conversation, some recovered art, and Amiigoose’s own hand-drawn illustrations of the game board. The rebuild started from there: port the recoverable gameplay logic to Godot 4, rebuild the scenes, and treat his art as the actual design document rather than a reference to eyeball once and forget.

Building a train that actually fights

Every combat car — the basic Gunner Car, the close-range Ballast Blaster, the splash-damage Coal Cannon, the burst-firing Chaingunner Car — shares one base class for targeting, rail patrol, and the firing timer, and overrides just the part that makes it different: what it fires, how it fires, and what it sounds like when it does. That structure is what let each of the four turrets get its own upgrade path without the underlying patrol/targeting code caring which weapon is mounted, and it’s the same reason four very different guns can each get a distinct sound from one shared firing method.

Keeping the artist’s board and the game’s grid honest

The hardest problem wasn’t a gameplay system — it was making sure Amiigoose’s hand-drawn board and the numeric grid the game actually runs on never quietly drifted apart. A drawing doesn’t come with rail spacing or lane centers built in; those have to be measured out and then re-checked every time the art changes. Rather than pass coordinates back and forth over Discord, I built a standalone “Artist Grid” view: it draws the real rail lattice, spider lane centers, and station leak line directly over his own illustrated board, reachable from a plain URL with no editor or build step involved. He can open it and see, at a glance, whether his art and my grid agree.

Where it stands

The project keeps a confidence-labelled wiki precisely because so much of its early history already turned out to be fragile — a link that worked in 2023 is a dead page now, and a message in a Discord DM is easy to lose track of. Everything in this write-up is grounded in what’s actually implemented: the Unity-to-Godot migration, four distinct turret types, a nine-archetype spider roster that unlocks across campaign progress, persisted campaign saves with a real Continue/Restart choice, a visual-novel-style tutorial, and the Artist Grid tool that keeps the whole thing honest against Amiigoose’s art as it keeps evolving.
