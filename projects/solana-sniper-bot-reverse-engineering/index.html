Solana Sniper Bot Reverse-Engineering

Creator·2026·5 min read

A forensic machine-learning investigation into how a live wallet selects pump.fun tokens in the zero block—and whether its decision rule can be replicated without looking into the future.

How the investigation is taking shape

Each phase has a clear output and a temporal boundary. That keeps the eventual model explainable and stops future chain activity leaking into the entry decision.

Phase 0 · Define the question

Reframe the task as policy reconstruction

The target is not simply buying tokens that later pump. It selects a small subset at deployment, before normal price discovery exists. The useful question is therefore: what information was visible when the wallet committed capital?

new deployment → information available now → buy / ignore
Core framing: this is a forensic decision-policy problem, not ordinary token-outcome prediction.
Phase 1 · Establish the behavior

Measure what the wallet actually does

Before proposing rules, the analysis maps every target-wallet entry and exit: deployment-to-buy latency, position inside the zero block, entry size, partial exits, holding time, realized P&L, and the distribution of wins and losses.

deploy event → target buy → exit path → trade-level outcome

The exit criterion for this phase is a reproducible trade ledger and an evidence-backed description of the bot's operating pattern.

Phase 2 · Build the decision table

Turn the chain into one row per candidate

Every eligible token deployment becomes a candidate, whether the target bought it or not. The row connects token metadata, deployer identity, prior wallet activity, funding relationships, and deployment-transaction context.

Phase 3 · Freeze time at deployment

Make leakage impossible by construction

Each feature receives an availability timestamp and explicit cutoff rule. Deployer history is calculated only from earlier launches; wallet activity stops at deployment; later bonding-curve movement and holder behavior never enter the selector.

feature event time <= t_decision → allowed   |   feature event time > t_decision → blocked
The non-negotiable rule: post-deployment data can evaluate whether a trade worked, but it cannot help decide whether to enter that trade.
Phase 4 · Test the signal families

Ask which pre-decision clues matter

The working hypotheses cover deployer reputation, wallet maturity, funding provenance, dev-buy intent, token metadata, launch timing, and wallet-network relationships. Each family is tested alone and then alongside the others.

Leading hypothesis: the bot recognizes operators and wallet clusters more than it predicts token narratives. Deployer history and funding relationships should therefore explain more selections than branding alone.

This remains a hypothesis until the timestamped decision table can support or reject it.

Phase 5 · Infer an explainable policy

Prefer a rule that can be challenged

A regularized logistic model establishes the transparent baseline. Attributed boosted trees test whether nonlinear interactions add useful signal. Both are scored on later time windows using PR-AUC, precision, recall, and F1 rather than class-imbalanced accuracy.

time split → baseline → attributed trees → top signals → plain-language rule

The model is useful only if its highest-ranked signals can be translated into a plausible description of how the target wallet chooses.

Phase 6 · Replicate under friction

Make the backtest earn its conclusion

The selection threshold is fixed on training and validation data, then applied to later deployments. The replica is compared directly with the target on selection overlap, P&L, hit rate, and drawdown.

lock threshold → score later launches → delay entry → apply fees / slippage → compare
Perfect execution is not the baseline. The report will show zero-block assumptions alongside one- and two-slot delay sensitivity so any apparent edge can be separated from impossible transaction ordering.
Phase 7 · Report what survived

Separate evidence from the working theory

The final case study will replace hypotheses with measured behavior, top feature contributions, held-out model quality, and matched-window trading results. Failed ideas and sensitivity tests stay in the record rather than disappearing behind the final score.

What the process is designed to protect

  • Feature timestamps are as important as feature values
  • Overlap with the bot and trading profitability answer different questions
  • Interpretability is part of the result, not presentation added afterward
  • An honest delayed-entry backtest is more useful than a perfect but impossible fill
