Solana Sniper Bot Reverse-Engineering

Creator·2026·5 min read

A forensic machine-learning investigation into how a live wallet selects pump.fun tokens in the zero block—and whether its decision rule can be replicated without looking into the future.

Overview

The target wallet buys only a subset of new pump.fun launches and enters in the same Solana slot in which each token is deployed. The project reconstructs what the wallet could know at that instant, builds an interpretable model of its selection behavior, and turns that model into a replica strategy evaluated under realistic execution conditions.

Problem

The bot acts before normal price discovery exists. Bonding-curve movement, later holders, future migration, and post-launch trading cannot explain its entry decision because none of those signals are available yet. The central problem is to identify which pre-decision signals separate the tokens it buys from the much larger universe it ignores.

Constraints

  • Every model feature must be available strictly before or at t_decision
  • No post-deployment price action, holder activity, migration outcome, or future deployer result may enter the selector
  • Training and evaluation must use chronological splits rather than random folds
  • The positive class is rare, making PR-AUC, precision, and recall more useful than raw accuracy
  • The backtest must expose fees, slippage, transaction ordering, and one- to two-slot entry delays

Approach

Each eligible deployment becomes one decision row connecting the token to its deployer, funding wallets, transaction context, metadata, and prior on-chain history. Every field receives an availability timestamp and is truncated at deployment. The investigation first measures the target wallet's actual entries and exits, then tests explainable feature families—deployer reputation, wallet maturity, funding provenance, dev-buy construction, metadata, timing, and network relationships. A final score or sparse rule set is locked on an earlier window and evaluated on later deployments.

Key Decisions

Make feature availability part of the schema

Reasoning:

Leakage is the defining risk, so temporal validity cannot be left to memory or a final review. Each feature needs a cutoff rule that can be audited in code.

Alternatives considered:
  • Build a conventional token-outcome dataset and remove suspicious columns afterward

Prefer an interpretable decision policy

Reasoning:

The goal is not only to classify buys; it is to explain the probable rule. Regularized logistic regression and attributed boosted trees make the signal inspectable.

Alternatives considered:
  • Optimize a large opaque model solely for leaderboard performance

Backtest the replica under execution friction

Reasoning:

A perfect zero-block fill can create an edge that does not exist in practice. Delay sensitivity, fees, slippage, and ordering assumptions stay visible in every comparison.

Alternatives considered:
  • Assume entry at the deployment price for every selected token

Tech Stack

  • Python
  • Solana on-chain transaction data
  • Time-aware feature engineering
  • Interpretable machine learning
  • SHAP and feature attribution
  • Out-of-time backtesting

Result & Impact

The project currently provides a structured research plan, entity model, leakage checklist, hypothesis set, and honest backtest specification. The next milestone is to map the supplied chain data into the timestamped candidate table and replace the working hypotheses with measured behavioral and model evidence.

Learnings

  • A zero-block strategy is a forensic decision-policy problem, not ordinary token-outcome prediction
  • Feature timestamps are as important as feature values
  • Overlap with the target wallet and trading performance answer different questions and both need reporting
  • An honest delay-sensitive backtest is more useful than an impressive result built on impossible execution
