Radio LLM

Creator · 2026 · 1 day · 1 person · 10 min read

A push-to-talk voice assistant that runs entirely on local hardware — a local DeepSeek model, local speech-to-text and text-to-speech, and a retrieval pipeline over a 9,000+ chunk personal radio-operator wiki — talks back like an actual radio, and never makes a single network call to anyone else's server.

Overview

Radio LLM is a hold-to-talk voice interface to a local LLM, built to feel like keying up a radio rather than opening a chat window. Hold a button (or the spacebar), speak, let go, and it transcribes you, retrieves relevant material from a personal wiki, asks a locally-running DeepSeek model, and speaks the answer back — all on one machine, with nothing sent anywhere else. The wiki behind it isn't a toy: it's grown into a genuine radio-operator reference library, combining hand-written procedure notes with full-text extracts of real signals manuals, antenna handbooks, and field guides, indexed as 9,313 searchable chunks.

Problem

I wanted to talk to a local model the way you'd talk over an actual radio channel — key up, speak, key off, get an answer back in voice — grounded in a wiki of my own reference material rather than the model's general training data alone. That meant wiring together four separate local systems (microphone capture, speech-to-text, retrieval-augmented generation, text-to-speech) that all had to run entirely offline on a single consumer GPU, and none of them were guaranteed to agree with each other's assumptions about hardware, APIs, or performance at the scale the wiki ended up growing to.

Constraints

  • Everything had to run locally — no cloud STT, TTS, or LLM calls, on a single RTX 3050 with 6GB of VRAM
  • "Push-to-talk" needed real hold-to-talk semantics (record while held, stop on release) — a terminal can't detect a key being released, only a GUI can
  • The wiki wasn't a handful of notes — it grew mid-build into 9,313 chunks pulled from full military reference manuals, and the retrieval pipeline had to stay usable at that scale, not just at demo scale
  • The GPU driver (used fine by Ollama directly) turned out not to be enough on its own for every local library that wanted CUDA - some needed their own separately-installed runtime
  • Library APIs for young, fast-moving local-AI tooling didn't match their own documentation by the time this was built, so the code had to be verified against what was actually installed, not what a guide said

Approach

The pipeline is five small modules instead of one script: audio_io.py captures the mic while a key is held and plays audio back, stt.py wraps faster-whisper, wiki_index.py chunks and embeds the wiki into a flat numpy+JSON vector store, llm.py builds the prompt and calls Ollama, and tts.py speaks the answer with Piper. A Tkinter GUI ties them together specifically because Tkinter gives real key-down/key-up events — the one thing a terminal-based push-to-talk can't do — plus a natural place to show radio-style status (STANDBY / RECEIVING / PROCESSING / TRANSMITTING) and a running transcript. Every one of the four local subsystems broke against real hardware and real data in a way its own documentation didn't warn about, and each fix mattered more than the original design: batching the wiki's embedding calls instead of sending one HTTP request per chunk, falling back to CPU for speech-to-text when the CUDA runtime the driver alone didn't provide turned out to be missing, and following the actually-installed TTS library's real API instead of the one its own docs still described.

Key Decisions

Build the push-to-talk interface as a small Tkinter GUI instead of a terminal app

Reasoning:

A terminal can tell you when a key goes down, but not reliably when it comes back up — there's no key-release event in a TTY. Genuine hold-to-talk needs both. Tkinter is stdlib, needs no extra install, and gives real KeyPress/KeyRelease events on both a button and the spacebar, plus a natural home for a radio-style status readout and live transcript log.

Alternatives considered:
  • A terminal app using press-Enter-to-start / press-Enter-to-stop instead of true hold-to-talk
  • A global OS-level hotkey library reading raw input devices, which needs elevated permissions and behaves inconsistently between X11 and Wayland

Batch the wiki's embedding calls instead of embedding one chunk at a time

Reasoning:

The wiki's first real build came out to 9,313 chunks once the radio-operator manuals were added, and the initial one-chunk-per-HTTP-call implementation was still grinding through them after many minutes with nothing to show for it — indistinguishable, from the user's side, from the app being broken. Sending the embedding model batches of 64 chunks per call instead of one dropped a warm batch to about half a second, taking the full first-time index build from an open-ended wait down to under two minutes, and a threading lock now stops a talk attempt mid-build from silently kicking off a second, duplicate rebuild in parallel.

Alternatives considered:
  • Leave it sequential and just tell the user the first run is slow
  • Reduce the wiki's chunk count instead of speeding up embedding, at the cost of retrieval precision

Run speech-to-text on CPU instead of chasing a GPU-only setup

Reasoning:

faster-whisper's CUDA path failed with a missing libcublas.so.12, even though the NVIDIA driver was fine and Ollama was already using the same GPU for the LLM and embeddings without issue — ctranslate2 needs its own separately-installed CUDA runtime, distinct from the driver. Rather than add a second CUDA runtime install just for short push-to-talk clips, transcription runs on CPU, where a few seconds of speech transcribes fast enough that the difference isn't noticeable in the radio's turnaround time, and the GPU stays free for the LLM and embeddings.

Alternatives considered:
  • Install a matching CUDA runtime (cuBLAS/cuDNN) system-wide just for faster-whisper
  • Switch to a different STT engine with simpler GPU requirements

Keep retrieval as a flat numpy+JSON store instead of a vector database

Reasoning:

A personal wiki, even at 9,313 chunks, is small enough that brute-force cosine similarity over a numpy array is fast and completely transparent to debug — the whole index is one readable JSON file. Pulling in a compiled vector-database dependency would have added real risk of wheel-compatibility headaches on a very new Python interpreter for no benefit at this scale.

Alternatives considered:
  • chromadb or another embedded vector database
  • A hosted vector search service (ruled out immediately - the whole point was staying local)

Tech Stack

  • Python 3.12 (chosen specifically over the system's newer 3.14 to avoid compiled-dependency wheel gaps)
  • Tkinter for the push-to-talk GUI and radio-style status/log display
  • Ollama running deepseek-r1:8b for chat and nomic-embed-text for embeddings, entirely local
  • faster-whisper (CPU) for speech-to-text
  • Piper for local text-to-speech
  • sounddevice/PortAudio for microphone capture and playback
  • A custom numpy + JSON vector store for retrieval — no external vector database

  • 9,313 indexed chunks across a personal radio-operator knowledge base

What started as a request for a local-only, radio-styled voice interface to a DeepSeek model turned into a genuinely useful reference tool: a working hold-to-talk assistant that can answer real radio-operator questions — antenna orientation to deny direction-finding, terrain masking, net procedure — by pulling grounded passages out of thousands of chunks of real reference material and folding them into a spoken answer, without a single byte leaving the machine.

Learnings

  • A slow first run and a broken one look identical to a user holding a button and hearing nothing back — the fix wasn't just making the wiki's first index build faster, it was making its progress visible at all
  • A file that looks fully downloaded by size alone can still be far from done — Ollama preallocates a model layer's full size on disk before the bytes have actually arrived, so watching file size instead of the daemon's own transfer log gave a false read on a stalled model pull
  • A GPU driver being enough for one local tool (Ollama, using it directly) doesn't mean it's enough for another (ctranslate2, which wants its own separately-installed CUDA runtime) — 'the GPU already works' isn't a safe assumption to carry between tools
  • Fast-moving local-AI Python packages can ship a real API that's already diverged from what a guide or an older example describes — the fix was checking the actually-installed library's own attributes rather than trusting either memory or documentation

Keying up to a local model

The goal was simple to say and less simple to build: talk to a local model the way you’d talk over an actual radio — hold a button, speak, let go, hear an answer back — with every piece of that pipeline running on the machine in front of me and nothing sent anywhere else. That’s four different local systems that all have to agree with each other: a microphone capture layer that knows exactly when a button goes down and comes back up, speech-to-text, a retrieval step over a personal wiki, a local LLM call, and text-to-speech.

Why a GUI, not a terminal

Push-to-talk only means something if release is detected as reliably as press. A terminal can catch a key going down; it generally can’t catch it coming back up, so a terminal-based “hold to talk” is usually a lie — really a toggle in disguise. Tkinter, despite being the plainest possible choice, gives real KeyPress/KeyRelease events on both a dedicated button and the spacebar, which is the one thing this project actually needed a GUI for. That same window became the natural home for a radio-style status readout — STANDBY, RECEIVING, PROCESSING, TRANSMITTING — and a running transcript log, so a slow or failed step is visible instead of silent.

The wiki grew past the design

The retrieval layer was designed around a handful of personal notes. Partway through the build, the wiki became a real radio-operator reference library — hand-written procedure notes on antennas, propagation, COMSEC, and net operation, plus full-text extracts of actual signals manuals, antenna handbooks, and field guides — and came out to 9,313 chunks once indexed. The original implementation embedded one chunk per HTTP call to the local embedding model, which meant the very first index build was still running after several minutes with no visible progress, and a second push-to-talk attempt during that window would silently trigger a second, duplicate rebuild in parallel. Batching 64 chunks into a single embedding call instead — with a lock so only one build can run at a time — took a warm batch down to about half a second, and the full 9,313-chunk build to under two minutes, with the GUI now showing live progress instead of leaving the button looking dead.

Two libraries, two surprises

Two of the four local subsystems broke against the real setup in ways their own documentation didn’t warn about. Speech-to-text’s CUDA path failed on a missing libcublas.so.12, even though Ollama was already running the LLM and embeddings on the same GPU without complaint — the driver was fine, but faster-whisper’s CUDA backend needs its own separately-installed runtime, and short push-to-talk clips transcribe fast enough on CPU that it wasn’t worth chasing. Text-to-speech failed differently: the installed version of Piper’s Python package no longer exposed the streaming-bytes method the original code called at all — its real API returns a different object type entirely. Both fixes came down to the same thing: checking what the installed library actually does, rather than trusting an assumption carried over from documentation or memory.

Where it stands

The result is a working local radio: hold to talk, get transcribed, get an answer grounded in real reference material when the wiki has it and the model’s own knowledge when it doesn’t, and hear it spoken back — the station’s callsign, if you ask, is “AM.” The wiki keeps growing, and every subsystem now reports its own state into the same log instead of failing silently, which turned out to matter more for a voice tool than for almost any other kind of app: when something goes wrong, “nothing happens” and “it’s still working” look identical unless the tool tells you which one it is.
