Radio LLM

Creator · 2026 · 3 days (ongoing) · 1 person · 15 min read

A local voice assistant that answers to its own callsign — say "AM" or its phonetic form "Alpha Mike" and it starts listening — speaking back in genuine radiotelephone procedure grounded in a real Australian Army RATEL manual, streamed sentence-by-sentence for a fast reply, and running entirely on local hardware with a 9,800+ chunk personal radio-operator wiki behind it.

Overview

Radio LLM is a voice interface to a local LLM built to feel like an actual radio net, not a chat window. In wake-word mode it listens continuously and only responds once it hears its own callsign — "AM," or the correct radiotelephone way to spell that out, "Alpha Mike" — then transcribes, retrieves relevant material from a personal wiki, asks a locally-running chat model, and streams the spoken answer back sentence by sentence as it's generated. A push-to-talk mode still exists as a manual fallback. The wiki has grown into a genuine radio-operator reference library: hand-written procedure notes plus full-text extracts of real signals manuals, antenna handbooks, field guides, and - now the primary style authority - the Australian Army Cadets' official RATEL (radiotelephone procedure) handbook, all indexed as 9,795 searchable chunks.

Problem

I wanted to talk to a local model the way you'd talk over an actual radio channel - key up, speak, key off, get an answer back in voice - grounded in a wiki of my own reference material rather than the model's general training data alone. That meant wiring together four separate local systems (microphone capture, speech-to-text, retrieval-augmented generation, text-to-speech) that all had to run entirely offline on a single consumer GPU. Once the basic loop worked, the harder problem showed up: making it fast and making it actually sound like a trained radio operator turned out to be in real tension with each other, and the fastest available model wasn't just less polished, it was factually wrong in ways a slower one wasn't.

Constraints

  • Everything had to run locally - no cloud STT, TTS, or LLM calls, on a single RTX 3050 with 6GB of VRAM
  • "Push-to-talk" needed real hold-to-talk semantics (record while held, stop on release) - a terminal can't detect a key being released, only a GUI can
  • The wiki wasn't a handful of notes - it grew to 9,795 chunks pulled from full military reference manuals, and the retrieval pipeline had to stay usable at that scale, not just at demo scale
  • A wake word needed to trigger on an extremely short, common word ("AM") without either false-triggering constantly or missing the actually-correct way a real operator would say it - spelled phonetically as "Alpha Mike," which speech-to-text often renders as "alpha mic"
  • Reasoning ("-r1") chat models could spend 20-30+ seconds "thinking" before the spoken answer even started, but the fastest non-reasoning alternative produced genuinely incoherent, self-contradicting answers on technical procedural questions - speed and correctness both had to hold, one couldn't quietly be traded for the other
  • Library APIs for young, fast-moving local-AI tooling didn't match their own documentation by the time this was built, so the code had to be verified against what was actually installed, not what a guide said

Approach

The pipeline is five small modules instead of one script: audio_io.py captures the mic (both hold-to-talk and a continuous wake-word listener), stt.py wraps faster-whisper, wiki_index.py chunks and embeds the wiki into a flat numpy+JSON vector store, llm.py builds the prompt and streams the reply from Ollama sentence-by-sentence, and tts.py speaks each sentence with Piper as soon as it's ready rather than waiting for the full answer. A Tkinter GUI ties it together with a mode toggle between wake-word and push-to-talk, and a radio-style status readout (STANDBY / LISTENING / RECEIVING / PROCESSING / TRANSMITTING). Wake-word detection reuses the STT that already had to exist rather than adding a dedicated acoustic keyword-spotting model: a lightweight RMS-energy voice-activity detector segments speech from silence, faster-whisper transcribes each utterance, and a regex checks whether it opens with the callsign - in either form. The chat model itself went through a real three-way bake-off against live questions rather than a spec-sheet comparison, because the two fast candidates that looked fine on simple prompts each broke in a different, model-specific way on harder ones.

Key Decisions

Build the push-to-talk interface as a small Tkinter GUI instead of a terminal app

Reasoning:

A terminal can tell you when a key goes down, but not reliably when it comes back up - there's no key-release event in a TTY. Genuine hold-to-talk needs both. Tkinter is stdlib, needs no extra install, and gives real KeyPress/KeyRelease events on both a button and the spacebar, plus a natural home for a radio-style status readout and live transcript log.

Alternatives considered:
  • A terminal app using press-Enter-to-start / press-Enter-to-stop instead of true hold-to-talk
  • A global OS-level hotkey library reading raw input devices, which needs elevated permissions and behaves inconsistently between X11 and Wayland

Detect the wake word by reusing the existing speech-to-text step behind a simple energy-based VAD, instead of a dedicated wake-word model

Reasoning:

"AM" is about the worst possible case for acoustic keyword-spotting - two letters, extremely common, easy to false-trigger on. Full ASR already has to run for every real question anyway, so segmenting speech with a lightweight RMS-amplitude voice-activity detector and transcribing each utterance with the STT that already exists costs nothing extra architecturally, and lets the wake-word check be a real regex against real transcribed text - including recognizing "Alpha Mike" (and Whisper's frequent mishearing "alpha mic") as the same callsign, since that's the actually-correct radiotelephone way to spell out a callsign that's just two letters.

Alternatives considered:
  • A dedicated offline wake-word model (e.g. openWakeWord/Porcupine), which would need custom training or an account/console step for a non-standard two-letter keyword
  • Recognize only the bare word "AM" and require users to say it unnaturally instead of the procedurally correct phonetic form

Stream the reply sentence-by-sentence into text-to-speech, and choose the chat model from a real three-way bake-off instead of picking one up front

Reasoning:

The first model tried, a "-r1" reasoning variant, produced well-formed radio-procedure answers but spent 20-30+ seconds generating internal reasoning before the spoken answer even began - streaming doesn't fix that, since there's nothing to stream until reasoning finishes. Switching to a faster non-reasoning model got replies starting in 2-7 seconds, but it broke down on technical questions into genuinely incoherent, self-contradicting text (a step under "lengthen the antenna" that talked about a volume control) - a correctness failure, not just a style one. A second non-reasoning candidate turned out to be both fast (often under 2 seconds once warm) and reliable: on a question the wiki didn't actually cover, it said so plainly and pointed at the manual instead of inventing a garbled procedure - exactly the "never guess" principle already in the system prompt, but only the third model tested actually held to it.

Alternatives considered:
  • Ship with the first working model and accept the multi-second silence before every reply
  • Ship with the fast model and accept that some technical answers would be wrong or incoherent

Ground the radio-operator persona in the actual Australian Army Cadets RATEL handbook, and strip source citations in code rather than trust the model to leave them out

Reasoning:

An earlier hand-rolled prowords/phonetic-alphabet list was a reasonable guess but not authoritative, and turned out to have real mismatches with official procedure (e.g. digit pronunciation). Extracting and indexing the actual RATEL manual - and rewriting the system prompt around its real SAD (Security, Accuracy, Discipline) and RSVP (Rhythm, Speed, Volume, Pitch) principles and its official 70-entry prowords table - fixed that at the source instead of guessing. Separately, just asking the model not to read bracketed source-filename citations out loud wasn't reliable enough on its own once retrieval got fully wired in, so the code now strips anything bracket-delimited from every sentence before it's spoken or logged, regardless of whether the model behaves.

Alternatives considered:
  • Keep hand-written procedure notes as the sole style authority instead of sourcing an official manual
  • Rely entirely on prompt instructions to suppress citation leakage, and accept the occasional slip

Batch the wiki's embedding calls instead of embedding one chunk at a time

Reasoning:

The wiki's first real build came out to over 9,000 chunks once the radio-operator manuals were added, and the initial one-chunk-per-HTTP-call implementation was still grinding through them after many minutes with nothing to show for it - indistinguishable, from the user's side, from the app being broken. Sending the embedding model batches of 64 chunks per call instead of one dropped a warm batch to about half a second, taking the full index build from an open-ended wait down to under two minutes, and a threading lock now stops a talk attempt mid-build from silently kicking off a second, duplicate rebuild in parallel.

Alternatives considered:
  • Leave it sequential and just tell the user the first run is slow
  • Reduce the wiki's chunk count instead of speeding up embedding, at the cost of retrieval precision

Run speech-to-text on CPU instead of chasing a GPU-only setup

Reasoning:

faster-whisper's CUDA path failed with a missing libcublas.so.12, even though the NVIDIA driver was fine and Ollama was already using the same GPU for the LLM and embeddings without issue - ctranslate2 needs its own separately-installed CUDA runtime, distinct from the driver. Rather than add a second CUDA runtime install just for short utterances, transcription runs on CPU, where a few seconds of speech transcribes fast enough that the difference isn't noticeable in the radio's turnaround time, and the GPU stays free for the LLM and embeddings.

Alternatives considered:
  • Install a matching CUDA runtime (cuBLAS/cuDNN) system-wide just for faster-whisper
  • Switch to a different STT engine with simpler GPU requirements

Keep retrieval as a flat numpy+JSON store instead of a vector database

Reasoning:

A personal wiki, even at close to 10,000 chunks, is small enough that brute-force cosine similarity over a numpy array is fast and completely transparent to debug - the whole index is one readable JSON file. Pulling in a compiled vector-database dependency would have added real risk of wheel-compatibility headaches on a very new Python interpreter for no benefit at this scale.

Alternatives considered:
  • chromadb or another embedded vector database
  • A hosted vector search service (ruled out immediately - the whole point was staying local)

Tech Stack

  • Python 3.12 (chosen specifically over the system's newer 3.14 to avoid compiled-dependency wheel gaps)
  • Tkinter for the GUI, mode toggle, and radio-style status/log display
  • Ollama running qwen2.5:7b-instruct for chat and nomic-embed-text for embeddings, entirely local, chosen after a real bake-off against deepseek-r1:8b and deepseek-llm:7b-chat
  • A simple RMS-energy voice-activity detector plus faster-whisper (CPU) reused for both dictation and wake-word detection
  • Piper for local text-to-speech, fed sentence-by-sentence as the reply streams in
  • sounddevice/PortAudio for microphone capture and playback
  • A custom numpy + JSON vector store for retrieval - no external vector database

Result & Impact

  • 9,795 indexed chunks, including the official Australian Army RATEL handbook
    Wiki scale
  • Down from 20-30+ seconds with a reasoning model to often under 2 seconds once the winning model is warm
    Reply latency (first spoken sentence)
  • Zero - speech-to-text, retrieval, generation, and speech synthesis are all local
    Network calls to build an answer

What started as a request for a local-only, radio-styled voice interface to a DeepSeek model became a genuinely disciplined radio operator: it answers to its own callsign spoken the procedurally correct way, streams a reply fast enough to feel conversational, follows real RATEL prowords and phonetic-alphabet convention, and - the part that mattered most once real technical questions started arriving - says plainly when its own wiki doesn't cover something instead of inventing a confident-sounding wrong answer.

Learnings

  • "Faster" isn't a single axis worth optimizing alone - a model that answers in 2 seconds but garbles a real procedure is worse than one that takes 20, and the only way to actually know which failure mode a given model has is to run it against real hard questions, not just admire how quickly it responds to easy ones
  • A wake word for a two-letter word is exactly the case where reusing full ASR beats acoustic keyword-spotting - and real usage immediately proved it mattered: a user naturally spelled a two-letter callsign out phonetically ("Alpha Mike") the correct radiotelephone way, which a keyword model tuned only for the bare word would have completely missed
  • A slow first run and a broken one look identical to a user holding a button and hearing nothing back - the fix wasn't just making the wiki's first index build faster, it was making its progress visible at all
  • A file that looks fully downloaded by size alone can still be far from done - Ollama preallocates a model layer's full size on disk before the bytes have actually arrived, so watching file size instead of the daemon's own transfer log gave a false read on a stalled model pull
  • Telling a model not to do something in the system prompt is a request, not a guarantee - citation leakage and source-text regurgitation both needed a code-level fix (stripping brackets, forbidding verbatim reference-copying explicitly) because prompt instructions alone weren't reliably obeyed once real retrieved content got messy
  • An extremely slow reply isn't always a code bug - one 42-minute response turned out to be GPU/CPU contention from an unrelated game running at the same time, which silently forced the model into partial CPU offload; worth checking system load before assuming the pipeline itself regressed

Keying up to a local model

The goal was simple to say and less simple to build: talk to a local model the way you’d talk over an actual radio - key up, speak, key off, hear an answer back - with every piece of that pipeline running on the machine in front of me and nothing sent anywhere else. That started as push-to-talk. It’s grown into something closer to an actual radio net: say the station’s callsign and it starts listening, answers in real radiotelephone procedure, and talks back fast enough that a conversation actually feels like one.

From push-to-talk to a wake word

Push-to-talk works, but it’s not how a radio net actually operates - you don’t hold a button, you call the station you want. Adding a wake-word mode meant continuous listening, which meant deciding how to detect “AM” reliably. A dedicated acoustic wake-word model is the standard answer, but those are built for longer, more distinctive phrases; a bare two-letter word is close to a worst case for false triggers. The fix was to not build a second detection system at all: a lightweight RMS-energy voice-activity detector segments speech from silence, the same faster-whisper transcription that already has to run for every real question runs on each segment, and a regex checks whether the transcript opens with the callsign. That immediately paid off in a way a pure acoustic model wouldn’t have: real radiotelephone procedure spells a two-letter callsign out phonetically - “Alpha Mike” - and speech-to-text often renders that as “alpha mic.” Because detection happens on real transcribed text, both forms just work.

The wiki grew past the design

The retrieval layer was designed around a handful of personal notes. It’s grown into a real radio-operator reference library - hand-written procedure notes on antennas, propagation, COMSEC, and net operation, plus full-text extracts of actual signals manuals, antenna handbooks, and field guides - and now includes the primary style authority: the Australian Army Cadets’ own RATEL (radiotelephone procedure) handbook. The system prompt was rewritten around that manual’s actual content instead of a hand-rolled guess - its real SAD (Security, Accuracy, Discipline) and RSVP (Rhythm, Speed, Volume, Pitch) principles, its official 70-entry prowords table, and its exact phonetic-alphabet and digit-pronunciation conventions. The index now sits at 9,795 chunks, built through a batched-embedding pipeline (64 chunks per call instead of one) that turned what was an open-ended multi-minute wait into a build that finishes in under two minutes.

A real three-model bake-off

The single biggest lever on how the assistant actually felt turned out to be which chat model answered. The first choice, a “-r1” reasoning model, produced solid radio-procedure answers but spent 20 to 30-plus seconds generating internal reasoning before the spoken reply even started - streaming sentence-by-sentence into text-to-speech doesn’t help when there’s nothing yet to stream. Switching to a faster non-reasoning model cut that to a few seconds, but it broke down hard on real technical questions: asked how to cut an antenna to length, it produced a numbered list where step “lengthen the antenna” included a line about adjusting a volume control - fluent-sounding, structurally plausible, and simply wrong. A third candidate turned out to hold both properties at once: fast (often answering in under two seconds once the model was warm) and, critically, honest about the gap - asked the same antenna question, it said the retrieved material didn’t cover cutting antennas to length and pointed at the manual instead of inventing a procedure. That’s the “never guess” instruction already sitting in the system prompt; only the third model actually followed it under real pressure.

What prompts alone couldn’t fix

Two other bugs showed up only once real wiki content was flowing through the pipeline, and both needed a code fix, not just a stronger instruction. The model would sometimes read retrieved source citations - bracketed filenames like [wiki/file.txt] - directly into the spoken answer, and occasionally it would lose its own identity mid-conversation, answering as a different, invented callsign instead of the station it actually was. Telling it not to do either in the system prompt helped but wasn’t reliable once retrieval got messy enough. The actual fix for citations was to strip anything bracket-delimited from every sentence in code before it reaches text-to-speech or the log, regardless of what the model does; the identity fix was making the system prompt explicit that “Alpha Mike” and “Allied Master Computer” both unambiguously mean the assistant itself, not some other station being addressed.

Where it stands

The result is a working local radio: say its callsign - “AM,” or the correct phonetic “Alpha Mike” - and it starts listening, transcribes, retrieves grounded material from its own wiki when the material exists, answers honestly when it doesn’t, and speaks the reply back sentence by sentence as it’s generated. It follows real RATEL procedure rather than an approximation of one, and every subsystem reports its own state into the same log instead of failing silently - which matters more for a voice tool than almost any other kind, because “nothing happened” and “it’s still working” sound identical unless the tool says which one it is.
