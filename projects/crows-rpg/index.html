Crows RPG

Creator · 2026 · 29 min read

I started with two rulebook PDFs and no digital tooling. I built a full character builder, compendium, campaign manager, and multiplayer VTT against them — then discovered, deep into the project, that they were the wrong rulebook. This is both stories: the build, and the pivot to rebuild it correctly against the real game.

1 / 21 Crows RPG

Overview

I started this project with two dense rulebook PDFs for a homebrew tabletop RPG my group was already playing, and nothing else — no API, no database, no digital tooling built around this book at all. I built a complete system against that source: a guided character builder, a computed sheet, campaign tools, and a server-authoritative multiplayer VTT with fog of war. Then, well into the project, I discovered the source itself was wrong — my group's actual game is a different, commercial title with the same name, currently in public playtest. What follows is both halves: the original build, and the audited, tested pivot to rebuild the rules layer against the real game without losing the architecture underneath it.

Problem

The problem at the table was ordinary and constant: character creation and rules lookups meant passing two PDFs around and hunting through extracted text for a table or cross-reference nobody could find quickly. The harder problem underneath it was that PDF extraction gives you words, not structure — tables and multi-column layout came out of extraction with cells reassociated in ways that looked plausible and weren't. A second, much later problem turned out to be worse: I had confidently resolved a name collision early on (a video transcript describing a different game with the same name), built months of real, tested software against what I'd resolved as the correct source — and that resolution was itself wrong. The actual game is the other one.

Constraints

  • The only source of truth was two PDFs with no existing structured data, API, or community tooling to build on
  • A plausible-looking but incomplete transcription is worse than an obviously-missing one, so partial data had to be visibly flagged, not silently presented as finished
  • Needed real, server-authoritative multiplayer (tokens, fog of war, combat turns) for people playing together, without trusting anything the client sends about ownership or visibility
  • One person building this alongside an active campaign, so the first release had to solve the most common player task well rather than chase full breadth of the rulebook up front
  • The real game turned out to be an in-development commercial title from a real publisher, currently in public playtest — its rules text is their copyrighted material, so this project (and this write-up) summarizes and references mechanics rather than bulk-transcribing rulebook prose or redistributing their art

Approach

I didn't choose a stack before auditing the material, and I built the first version in good faith against what I'd identified as the source rulebook: PDF → reviewed Markdown wiki → generated JSON compendium, a character builder and sheet grown from that data, campaign tools, and a server-authoritative multiplayer VTT with fog of war — a complete, tested system. Then I found out the identification itself was wrong. Rather than patch around it, I stopped, audited exactly what was reusable versus what had to be rebuilt, rewrote the data model against the real rules, and rebuilt the character-creation and combat layers on top of it — all while a real, already-deployed production database had to survive the transition without losing anyone's data.

Key Decisions

A reviewable Markdown wiki between the PDFs and any generated data, instead of parsing PDF text straight into the compendium

Reasoning:

My first instinct was the more direct path — parse the extracted PDF text and clean up bad records as they surfaced. That fell apart specifically on the book's tables and columns: extraction reordered cells in ways that looked plausible but weren't, and a wrong number turned into a real rule the moment it reached the app with nobody checking it first. I introduced the wiki as a forced review step instead, with pages still needing work explicitly left as stubs. This same discipline — review before it becomes code-driving data — is exactly what the later rulebook-identity audit reused: don't touch more code until a written document says what's actually reusable.

Alternatives considered:
  • Parse PDF text directly into the database and clean up records after the fact
  • Hand-author JSON compendium records from scratch without a wiki intermediate

A server-authoritative WebSocket command pipeline, once a normal REST API wasn't enough for real-time play

Reasoning:

Scenes and tokens started as an extension of the same REST API, and that worked for authoring a scene alone. It broke down the moment more than one person needed to see the same token move, the same fog reveal, or the same combat turn advance without refreshing. I could have synced raw client state directly over WebSockets and validated it only at the REST layer, but that means trusting a player's own browser about its own token ownership or vision radius. Instead every intent now travels as a command the server validates for permission before persisting and broadcasting it — and this pipeline survived the entire rules pivot untouched, because it was never coupled to what a token's stats actually meant.

Alternatives considered:
  • Sync raw client state directly over WebSockets and validate only at the REST layer
  • Skip real-time sync and refresh scene state on a polling interval

Stopping to write a full migration audit before touching another line of code, once the wrong-rulebook mistake surfaced

Reasoning:

I'd already rewritten the character schema and half-built the new test engine when I caught myself — nothing downstream had been updated yet, and I was about to just keep going feature by feature, guessing at what else needed to change. Instead I stopped and wrote a row-by-row audit (old feature, new rule, status: keep/modify/replace/remove/blocked) before writing anything else. That document caught a real bug before it shipped: my half-remembered plan for the new wound mechanic was wrong — a wounded inventory slot doesn't become unusable and drop its item, it coexists with the item at a Speed penalty. I'd have built the wrong version of a system I hadn't even started yet if I'd kept moving without auditing first.

Alternatives considered:
  • Keep implementing feature-by-feature and fix mismatches as they're noticed in testing
  • Revert the schema change and re-plan from scratch before writing any new code

Idempotent, backed-up migration tooling tested against a real copy of production-shaped data, not just a fresh test database

Reasoning:

A first attempt at migrating the character schema worked perfectly against fresh, empty test databases and then failed with a real foreign-key violation the moment I ran it against my own populated local database — SQLite's per-transaction FK enforcement quietly doesn't disable the way a naive script assumes, and a table with real rows exposes that in a way an empty one never will. Rather than patch that one script, I built a read-only preflight report, a mandatory real backup step, and an idempotent migration command, then tested all of it against an actual copy of the pre-migration database with its real rows — not a synthetic fixture. That caught a second, unrelated bug (a `process.exit()` inside a `try` block silently skipping its own cleanup) that only a real destructive-replay test would have found.

Alternatives considered:
  • Trust the migration script after a code review and run it directly against production
  • Migrate the schema by hand once via direct SQL, skipping reusable tooling

Tech Stack

  • TypeScript (pnpm workspaces: server, web, shared schema)
  • Fastify (REST API) + ws (server-authoritative WebSocket channel)
  • Vue 3 + Vite (frontend), Pinia (state), PixiJS (VTT canvas rendering)
  • SQLite + Drizzle (schema/migrations, including hand-written destructive-migration tooling)
  • Zod (shared client/server schema validation)
  • Vitest (backend tests, incl. real WebSocket integration tests and a real production-data-shaped migration fixture)
  • Docker + Railway (production deployment, split from a GitHub Pages-hosted static frontend)

By the end of this build, there are honestly two results layered on top of each other. The first is a complete, tested character-builder/compendium/campaign/VTT system, built against what I believed was the source rulebook — proven end to end, including a full Docker build-and-run smoke test. The second, built on top of it without throwing the architecture away, is the same system rebuilt against the real rulebook once I found out the first one was wrong: a new 2d10 tier-test engine, Background-only character creation, a real equipment/damage chain, and a VTT combat bar that now matches the actual game — all migrated onto a live, already-populated production database without losing anyone's characters.

Learnings

  • Putting a reviewable Markdown intermediate between raw extraction and machine-readable data caught structural ambiguity before it could become a silently wrong rule — and the same discipline (write the audit before touching more code) is what caught the rulebook-identity mistake from compounding further
  • Resolving a name collision correctly once doesn't mean it stays resolved — the same 'there's more than one game called this' problem returned, much later and much bigger, and the only real defense is being willing to re-open a settled question when new evidence shows up
  • Three unrelated-looking 'stuck loading' screens turned out to be one root cause: an unhandled exception in an `await` with no `try/catch` looks identical to three separate bugs until you notice they all share the same shape
  • Testing a destructive schema migration against a full copy of real, populated production-shaped data — not just a fresh empty database — caught a transaction/foreign-key bug that no amount of testing against clean fixtures ever would have
  • Verifying a deploy actually landed (fetching the live JS chunk, watching the boot log, checking the database schema over SSH) is not optional once 'I pushed the code' and 'the server is running the new code' have become two different claims

Where I started

I started this project with two dense rulebook PDFs for a homebrew tabletop RPG that my group was already playing, and nothing else. No API, no database, no structured data, no digital tooling built around this book at all. The actual problem at the table was ordinary and constant: character creation and rules lookups meant passing PDFs around and hunting through dense, extracted text for a table or a cross-reference nobody could find quickly.

Early on, I hit a name collision — an auto-generated video transcript that seemed like useful supplementary material actually described a completely different, unrelated game that happened to share the title “Crows.” I treated it as an identity problem, compared the two rule sets directly (classes vs. no classes, d20 vs. 2d10, mana vs. no mana), and confidently wrote down which one this project implemented. At the time, that felt like due diligence. It turned out to be wrong — just not in a way I’d find out for months.

Getting the rules out of PDFs

The first real problem wasn’t which framework to use. It was that PDF extraction gives you words, not structure. The rulebook’s tables and multi-column layout came out of extraction with cells reassociated in ways that looked plausible and weren’t, and cross-references lost their anchors entirely. That’s a genuinely dangerous failure mode for a rules engine: a wrong number sitting quietly in a table becomes a real, silently broken game rule the moment something parses it straight into data nobody reviews.

My first instinct was the more direct path — parse the extracted text and fix records as errors turned up. That puts the review step after the data is already live in the app, which is backwards for a system where a broken formula changes what happens at an actual table. Instead I put a Markdown wiki between the PDFs and anything machine-readable: the PDFs stay the visual source of truth, the wiki is where a page gets checked against the source page by page, and dedicated converter scripts are the only thing allowed to turn reviewed wiki content into compendium records. Pages still needing work stay explicit stubs, and the converters skip them rather than seeding the compendium with something that only looks finished.

PDF → reviewed Markdown → generated JSON became the shape everything else grew from — and, months later, it’s exactly the same discipline that saved the pivot from becoming a worse mess than it needed to be.

The first time I looked at it

Before any of this had a UI, it had an API only. The first real milestone wasn’t a screen — it was one species and one class transcribed all the way through, converted, and validated: a character-creation request now got rejected with a 400 if it named a species or class the compendium didn’t actually contain, and a real sheet came back computed from real ability scores instead of a stored placeholder.

From there I built through essentially the rest of the planned system in one continuous push: the guided character-creation wizard, the sheet view, the searchable compendium browser, campaign tools, and a first version of the VTT — scenes, tokens, a WebSocket game channel, a combat tracker, walls, and fog of war — all landed together, verified at the API and WebSocket level, before ever opening it in a browser.

The screenshots below are the direct result of finally doing that — opening a browser and clicking through the whole thing for the first time. The very first pass through the VTT view found a real layout bug — its sidebar was cut off past the edge of the viewport, because the app’s global content-width cap didn’t leave room for a battlemap canvas plus a sidebar. I fixed it by letting that one route opt out of the width cap, then re-verified in a fresh session.

The character builder’s species step is sparse in this early capture because only one species was fully transcribed at that point — proof its options came from real compendium data rather than hardcoded UI choices, not yet proof of breadth. The compendium browser shows 59 total records, with several categories still sitting at zero. I left those empty counts visible rather than hiding them, because they were a more honest status report than any written note would have been.

Building character creation

Underneath those screens sat the same generated data — the character builder’s pickers, the sheet’s computed stats, and the compendium’s searchable list all read from the same generated records, not three separate implementations. Broadening past the first species/class pair was mechanical repetition of the same converter pattern rather than new architecture, and it’s where a couple of real transcription bugs surfaced: a parser undercount that silently dropped data from most entries in one category, and later a stat-block parser whose label-matching regex quietly dropped an entire boss monster’s content because its heading had an unexpected parenthetical in it. Both were caught by actually inspecting the generated output record by record, not by trusting that the conversion script ran without errors.

The compendium browser itself changed a lot more than its record count between two later screenshot sessions. An early capture shows a plain card-list UI still proving the data pipeline worked at all. By a later session, it’s a redesigned two-page “book” — search, a category rail down the side, and an entry rendered like a real page, complete with a bookmark ribbon. The header read 365 featured entries at that point — the same generated data from the same pipeline, just a lot more of it, and a UI that had by then earned a presentation to match.

A “Your Characters” library also appeared once there was more than one character worth listing — a searchable, filterable grid of cards with a detail panel for whichever one is selected.

Building the character sheet

A character sheet that shows derived stats is only useful if those numbers are actually correct, and I didn’t want a second, hand-maintained copy of the book’s formulas living in application code that could quietly drift from the real rules. Every formula the book used fit a small expression grammar, so I built a sandboxed evaluator for exactly that grammar, with no arbitrary code execution — the same “small, deterministic, testable module, not a general scripting language” philosophy I’d later reuse for a completely different rules engine, once I found out this one was for the wrong game.

Expanding into campaign management

Campaigns, journals, quests, and NPCs weren’t a separate feature phase so much as things that turned out to be missing the moment I actually tried to use the tool as a GM. Journals split into GM-only and everyone-visible entries, filtered server-side rather than just hidden in the UI, and NPCs got the same treatment: a GM’s secret notes are stripped out of the response for a non-GM request before it ever leaves the server.

The campaign list grew a second dimension over time — public discovery and join-by-code alongside a private list — and the campaign detail page grew into a real session control surface: status, live party stats, who’s actually connected, and campaign notes, all in one place once there was a live session worth representing.

The project becomes a VTT

Scenes and tokens started as an extension of the same REST API, and that worked fine for authoring content alone. It stopped working the moment more than one person needed to see the same token move, the same fog reveal, or a combat turn advance, without everyone refreshing to find out.

I considered syncing raw client state over WebSockets and only validating it once it hit the REST layer, but that means trusting a player’s own browser about its own token ownership or vision radius. Instead every scene, token, chat message, dice roll, and fog reveal travels as one intent over a per-campaign WebSocket channel, rendered on a PixiJS canvas, and the server checks permission on every single message before it’s persisted or broadcast.

Improving the VTT — the first ruleset’s version

The right-hand rail was rebuilt from a fixed inventory panel into a contextual GM Inspector that follows whatever’s selected. With nothing selected it shows scene-level tools and a combat header; selecting a token swaps it to that token’s own state, and the action bar below showed a shared pending-action model with real AP costs.

Walls backed up movement-blocking directly too — placing one meant picking a real type (Solid, Door, Window, Terrain, Invisible), each with its own vision/movement behavior.

Fog of war

Fog of war was the one place in the project with real, unavoidable geometry risk. The precise approach — a true visibility-polygon sweep — is substantial, non-trivial work on its own. I shipped a simpler version first: for every grid cell inside a token’s vision radius, check whether there’s an unobstructed line to it against the scene’s drawn walls. That later got refined into three visual states — current line of sight at full brightness, explored-but-not-visible terrain as a dim memory layer, and truly unknown terrain nearly opaque — so an explored room doesn’t visually imply a creature is still standing in it.

Testing and hardening

The test suite grew in step with each layer rather than being bolted on afterward. REST endpoints got ordinary integration tests. The WebSocket layer needed something stronger: real client connections opening actual sockets against a running server, not a mocked transport, exercising token movement, chat, dice rolls, combat turn order, and fog of war’s wall-blocking through the same authorization path a real player’s browser would use. On top of that, a full Docker build-and-run smoke test exercised migrations, the compendium seed, the API, and the served frontend together — so “the tests pass” and “a fresh deployment actually boots” were both checked, not assumed to imply each other. This discipline is what made the much harder testing problem later — a live database migration that could not be allowed to fail — survivable rather than terrifying.

The name I’d already resolved, wrong

Deep into the project, working through a much later phase of the build, I discovered that the entire implementation had been built against the wrong rulebook.

The name collision I’d resolved early on — “there’s a different game also called Crows” — turned out to be the collision, just pointed the wrong way. The game my group actually plays is that other one: an in-development commercial title from a real publisher, currently in a public playtest with its own official rulebook PDF. Everything I’d built — the species/class system, the six ability scores, HP and Mana and Armor Class, the whole formula grammar — was a complete, well-tested implementation of a different, unrelated homebrew book with the same title.

I don’t know exactly when or how the original identification went wrong, and I’m not going to pretend I do. What I do know is what happened once it surfaced: I stopped adding features and started auditing.

Stopping to write the audit before writing any more code

I’d already started reacting — rewriting the character schema, sketching a new dice-test engine — before catching myself mid-change. Nothing downstream had been updated yet, and continuing feature-by-feature meant guessing, over and over, at what from the old system was actually still valid.

Instead I stopped and wrote a row-by-row migration audit: every old feature, the corresponding real rule, and an explicit status — keep, modify, replace, remove, or blocked-pending-more-source-material. Writing that document caught a real bug before it ever shipped. My working plan for a not-yet-built wound mechanic had a wounded inventory slot become unusable and auto-drop whatever was in it. The real rule is smaller and stranger: a wound and an item coexist in the same slot, at a Speed penalty, and a character only dies once every slot is wounded. I’d have shipped the wrong version of a system I hadn’t even started, if I’d kept moving without writing that audit first.

What actually changed

Summarizing only — the actual rule text belongs to its publisher, not this write-up. Six ability scores became three characteristics. A d20-vs-Armor-Class attack roll became a 2d10 test read against result tiers. HP and Mana became a single Stamina pool. Species and class disappeared entirely — character creation now runs entirely off a rolled or chosen Background, of which there are three dozen. A flat pool of action points became one Maneuver plus one Action, or two Maneuvers, each round. A generic “conditions” free-text field became a fixed, small set of named conditions with real mechanical hooks.

None of this was guesswork. Once the real Characters booklet was in hand (more on how I found it below), a research pass transcribed the Background table’s mechanical fields — characteristic adjustment, starting Stamina, starting equipment, expertise grants — the same way every earlier compendium category had been transcribed: reviewed, generated by script, never hand-typed en masse.

Three stuck-loading screens, one root cause

With the new schema compiling and the tests passing, the actually-running app told a different story: the character list hung forever on “Loading your characters…,” opening a campaign hung forever on “Gathering the party…,” and the compendium loaded its shell but reported zero entries. Three screens, three apparently separate bugs — except all three shared one suspicious shape: infinite loading, never an error message.

The real cause was one migration that had been generated and verified against fresh, empty test databases, but never actually applied to the real local database underneath the new server code. Every character query threw an error for a column that no longer existed, and every screen that awaited that call without a try/catch — all three did — simply never reached the line that would have turned off its loading spinner. Not a crash. Not an error. Just silence, forever.

Fixing the actual bug (running the migration) wasn’t the whole fix. I added real loading/success/empty/error states — each with a retry action — to every screen this touched, because a failed request should never leave a screen looking like it’s merely still working.

Making a schema migration safe for a database that’s actually in use

Running that migration against my own real, populated local database — not a fresh test one — immediately failed with a foreign-key violation the naive version of the script had no way to anticipate. SQLite’s per-transaction foreign-key enforcement quietly doesn’t disable the way a script might assume once it’s already inside a migration transaction, and a table full of real rows exposes that in a way an empty table never will.

I didn’t patch that one script. I built a read-only preflight report (schema state, a foreign-key check, a count of not-yet-migrated rows, disk space, last backup — nothing mutated), a mandatory real backup step using SQLite’s actual Online Backup API, and an idempotent migration command safe to run more than once. Then, instead of trusting any of it by inspection, I copied my own real pre-migration database — every row, not a synthetic approximation — into a committed test fixture, and had the test suite run the actual migration logic against it: every row count preserved, every foreign key still resolving, a simulated crash at the two points that could plausibly happen mid-migration, and a confirmed clean recovery on retry either way.

That process caught a second, unrelated bug a code review alone wouldn’t have: an early version of the migration CLI called process.exit() from inside a try block wrapping an already-acquired lock file. process.exit() skips any pending finally — so every single run, including a totally successful no-op, silently leaked a stale lock that never got cleaned up. Only a real test of the script’s actual exit behavior caught it.

Finding the real rulebook, and building character creation for real

Character creation, advancement, and the item catalog were all explicitly delegated by the core rulebook to a separate “Characters” booklet nobody had a copy of — every character-creation row in the migration audit sat marked blocked. A web search for the game’s actual title (rather than the name it shared with the wrong book) turned up the real publisher and, with it, a free official playtest packet containing all four planned rulebooks. Once the Characters booklet was actually in hand, character creation, advancement, and roughly 276 individual character traits across two dozen trait trees all became real, specified systems instead of open questions.

I rebuilt the character creator to run the real procedure — roll or choose a Background, resolve its characteristic grant, assign the remaining two characteristics from a fixed pair of options, take starting Stamina and equipment from the Background — and rebuilt combat to match: real weapon and armor compendium entries, an Armor-Defense-then-Stamina damage chain with a piercing flag that skips absorption, and a server-rolled starting-gold roll rather than anything the client could supply. A GM or player selects a real weapon now instead of typing a dice expression that was never actually connected to anything.

The old characters didn’t just quietly disappear, either. Every character created before the migration got tagged with a visible “Legacy · Needs Playtest 2 Migration” badge everywhere it renders, rather than being silently left with zeroed-out stats that looked like real data.

Redeploying, and making sure it actually landed

None of this mattered until it reached the same production database real players use. I checked its actual state directly over SSH rather than assuming — schema version, a foreign-key check, exactly how many legacy characters existed — before generalizing the migration tool to handle production’s real starting point, which turned out to be one step further behind than any test fixture had assumed.

A second, more dangerous problem surfaced in the same check: the deploy container’s boot command ran the plain, unsafe migrator on every single startup. Shipping the new code as-is would have triggered the exact failure this entire migration effort existed to prevent, automatically, the moment the container booted, with no human able to review a preflight report first. I replaced the boot sequence with the safe tool first, the normal migrator second — a sequence that’s a safe no-op both on a brand-new database and once already migrated, so it’s fine to leave in place permanently rather than just for this one deploy.

Later, after actually pushing, a report came back that production still showed an old “character creation is being migrated” placeholder — the real, tested Background-driven creator had been built and verified locally but never actually reached Railway. I don’t take “the deploy command exited 0” as proof anymore. I fetch the live JavaScript chunk directly by URL and check for the strings that should be in it, and I watch the actual boot log for the exact sequence I expect, before calling a deploy done.

The map catches up to the new rules

The VTT still worked mechanically after the schema pivot, but its map still showed the old flat action-point bar, and it trusted the browser to keep an attack within range using plain circular distance — the real rules use squares, count diagonals normally, and require an unobstructed line of effect, not just line of sight.

The action bar became one Maneuver, one Action, and one Reaction — a Maneuver can use its own slot first and then consume the Action slot, producing the book’s actual “one Maneuver plus one Action, or two Maneuvers” turn. Range previews now use square distance with each weapon’s real reach, and a wall or closed door now shows a blocked-line-of-effect error instead of silently letting an attack through. Attack results float their real outcome over the target, and tokens display real condition badges instead of identical dots. And critically, the same validation now runs server-side too — a forged WebSocket message can’t attack across a scene, exceed a weapon’s range, or shoot through a wall the client’s own renderer might get wrong; the client preview is guidance, the server rule is authority.

Where it ended up

There are honestly two builds here, one on top of the other. The first is a complete, tested character-builder/compendium/campaign/VTT system, built and deployed against a rulebook that turned out to be the wrong one — real architecture, real tests, real production use, just aimed at the wrong game. The second, built without throwing that architecture away, is the same system migrated onto the real rulebook: a compendium now holding 91 real entries (36 Backgrounds, 25 weapons and armor, plus rules, expertise, condition, maneuver, and reaction entries), a character sheet with no HP or Armor Class left in it at all, a combat system that resolves through real equipped weapons and a real damage chain, and a VTT whose action economy, range rules, and line-of-effect checks match the actual game rather than a plausible-looking approximation of it. 118 or more tests pass, including a migration test suite that replays the real production schema change against a real copy of production-shaped data, not a synthetic stand-in.

The database migration itself — safe, backed-up, idempotent, tested against real data, verified live over SSH before and after — is arguably the most technically serious thing this project has produced, precisely because it had to work exactly once, against data that mattered, with no room for “close enough.”

What still isn’t finished

The rebuild is honestly less complete than the system it replaced, and that’s a real, visible state rather than a hidden gap. Expertise tracking, character advancement, and the ~276 individual character traits are transcribed and counted but not yet wired into character creation or the sheet. The Village system — institutions, Prosperity, retirement — exists in the source material but not in code. Usage Dice, Dungeon Turns, spellcasting, crafting, and pets/hirelings are all real systems in the rulebook with nothing built against them yet. Overland travel is flagged as a likely permanent scope cut — it doesn’t obviously fit a VTT built around battlemap scenes. The Ref Book and Dungeons Book (monster stats and premade adventure content) are downloaded but not yet read, and a favor column that’s existed in the schema since before any of this happened still hasn’t turned up in any rulebook read so far — it may simply be a leftover house rule waiting to be removed rather than implemented. None of this is hidden; it’s the explicit, audited edge of what “done” currently means, written down in the same document that’s tracked every other stage of this rebuild.
