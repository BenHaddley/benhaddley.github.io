Crows RPG

Creator · 2026 · 23 min read

I started with two rulebook PDFs and no digital tooling at all. This is how that became a character builder, a compendium, campaign tools, and a server-authoritative multiplayer VTT — one problem, one decision, and one converter pattern at a time — for a homebrew tabletop RPG my group actually plays.

Overview

I started this project with two dense rulebook PDFs for a homebrew tabletop RPG (Crows RPG 1.8.1) my group was already playing, and nothing else — no API, no database, no structured data, no digital tooling built around this book at all. What follows is the order I actually built it in: turning the PDFs into reviewable, then machine-readable, data; a character builder and sheet grown from that data; campaign tools that turned out to be missing the moment I tried to run a session; and a server-authoritative multiplayer VTT once a normal request/response API stopped being enough for people moving pieces on a shared map.

Problem

The problem at the table was ordinary and constant: character creation and rules lookups meant passing two PDFs around and hunting through extracted text for a table or cross-reference nobody could find quickly. The harder problem underneath it was that PDF extraction gives you words, not structure — the book's tables and multi-column layout came out of extraction with cells reassociated in ways that looked plausible and weren't, which is a dangerous failure mode for anything meant to compute real game rules. I also had a licensing line to respect before writing a line of code: only the rulebook's CC-BY-4.0 rules chapters (species, classes, combat, equipment, spells, the bestiary) could become mechanics — lore, setting text, and all artwork stayed all-rights-reserved.

Constraints

  • The only source of truth was two PDFs with no existing structured data, API, or community tooling to build on
  • Only the rulebook's licensed chapters (CC-BY-4.0) could be transcribed as mechanics; lore, setting text, and all artwork are excluded and stay all-rights-reserved
  • A plausible-looking but incomplete transcription is worse than an obviously-missing one, so partial data had to be visibly flagged, not silently presented as finished
  • Needed real, server-authoritative multiplayer (tokens, fog of war, combat turns) for people playing together, without trusting anything the client sends about ownership or visibility
  • One person building this alongside an active campaign, so the first release had to solve the most common player task well rather than chase full breadth of the rulebook up front

Approach

I didn't choose a stack before auditing the material. The real path was: turn the PDFs into a reviewable Markdown wiki, then generate JSON compendium records from the reviewed pages, then prove the whole spine on exactly one species and class pair before broadening it. From there I built through the rest of the planned system — character builder, sheet, compendium browser, campaign tools, and a first VTT — in one continuous push, verified at the API and WebSocket level, before ever opening it in a browser. Only after that did I actually look at it running, catch the first real layout bug, and keep iterating on the VTT specifically — walls, a GM inspector, fog rendering, a monster compendium, attack rolls — as its own extended round of work once the rest of the system was already usable.

Key Decisions

A reviewable Markdown wiki between the PDFs and any generated data, instead of parsing PDF text straight into the compendium

Reasoning:

My first instinct was the more direct path — parse the extracted PDF text and clean up bad records as they surfaced. That fell apart specifically on the book's tables and columns: extraction reordered cells in ways that looked plausible but weren't, and a wrong number turned into a real rule the moment it reached the app with nobody checking it first. I introduced the wiki as a forced review step instead — 100 Markdown pages, each one cross-referenced back to its source PDF page, with pages still needing work explicitly left as stubs. Converter scripts only ever read from the reviewed wiki, never from raw extracted text, and skip any page still marked a stub — so a plausible-looking but unfinished page can't silently seed the compendium.

Alternatives considered:
  • Parse PDF text directly into the database and clean up records after the fact
  • Hand-author JSON compendium records from scratch without a wiki intermediate

A small constrained formula grammar for derived stats, once hardcoding formulas by hand stopped scaling

Reasoning:

Once the character sheet needed to show real numbers, I had two obvious paths: hardcode each species/class's formula as bespoke server code, or reach for a full rules-scripting DSL for maximum flexibility. Hardcoding didn't survive past the first species/class pair, and a full DSL was real power — and a real security surface — the project didn't actually need, since every formula the book uses (1dHD + CON modifier for HP, HD + 2×CON for Mana, 10 + DEX + armor + bonus for AC) fits a tiny expression grammar. I built a sandboxed evaluator for exactly that grammar instead, with no arbitrary code execution, and it's covered every formula the rulebook has needed so far.

Alternatives considered:
  • Adopt a full rules-scripting DSL for maximum future flexibility
  • Hardcode each derived-stat formula as bespoke server code per species/class

A server-authoritative WebSocket command pipeline, once a normal REST API wasn't enough for real-time play

Reasoning:

Scenes and tokens started as an extension of the same REST API, and that worked for authoring a scene alone. It broke down the moment more than one person needed to see the same token move, the same fog reveal, or the same combat turn advance without refreshing. I could have synced raw client state directly over WebSockets and validated it only at the REST layer, but that means trusting a player's own browser about its own token ownership or vision radius. Instead every intent — move a token, reveal fog, advance a turn — now travels as a command the server validates for permission before persisting and broadcasting it, on every message, not just once at connection time.

Alternatives considered:
  • Sync raw client state directly over WebSockets and validate only at the REST layer
  • Skip real-time sync and refresh scene state on a polling interval

Radius-plus-wall-blocking fog of war, shipped before a true visibility-polygon sweep

Reasoning:

A precise visibility-polygon algorithm was the approach I actually wanted eventually — it's what the more mature prior-art VTT projects use — but it's real, non-trivial geometry work on its own, and building it before anything else worked wasn't the right order of operations. I shipped a simpler version first: for every cell inside a token's vision radius, check for an unobstructed line to it against the scene's walls. That gave real wall-blocking and a permanent explored-memory layer immediately, and I documented the upgrade path rather than pretending the simpler version was the precise one.

Alternatives considered:
  • Build the full visibility-polygon sweep algorithm before shipping any fog of war
  • Ship fog of war as a simple radius reveal with no wall-blocking at all

Tech Stack

  • TypeScript (pnpm workspaces: server, web, shared schema)
  • Fastify (REST API)
  • ws (server-authoritative WebSocket channel)
  • Vue 3 + Vite (frontend)
  • Pinia (state) + PixiJS (VTT canvas rendering)
  • SQLite (single-volume, Docker-deployed)
  • Zod (shared client/server schema validation)
  • Vitest (backend tests, including real WebSocket integration tests over an actual ws client)

By the end of this build, the full spine works end to end for real use: log in, build a character with the guided wizard against real compendium data, see a live computed sheet, join a campaign, open its map, drag tokens, roll initiative, and reveal fog — verified with a full Docker build-and-run smoke test (migrations, seeding, API, and served frontend together), not just type-checked. Known gaps are called out rather than hidden: HP is only computable at character level 1 since no leveling-up flow stores per-level hit-die rolls yet, sheet-level HP/condition edits made outside the VTT don't push a live WebSocket update to other viewers, and campaign invitations are still a GM-adds-by-email stand-in rather than real time-limited invite codes.

Learnings

  • Putting a reviewable Markdown intermediate between raw PDF extraction and machine-readable data caught structural ambiguity (tables, columns, cross-references) before it could become a silently wrong rule in the app
  • A constrained formula grammar for derived stats covered every formula the rulebook actually needed, without taking on a general scripting DSL's security surface
  • Verifying at the API/WebSocket level isn't the same claim as verifying in a browser — the first real click-through found a layout bug that no amount of passing backend tests could have caught
  • Server-authoritative validation on every WebSocket event, not just at connection time, is what actually makes ownership and fog-of-war guarantees hold up against a client that can't be trusted
  • Calling out known gaps explicitly (level-1-only HP, no live sheet push, email-based invites) kept the honestly-scoped first release shippable without pretending it was more complete than it was

Where I started

I started this project with two dense rulebook PDFs for a homebrew tabletop RPG — Crows RPG 1.8.1, from Clockwork Raven — that my group was already playing, and nothing else. No API, no database, no structured data, no digital tooling built around this specific book at all. The actual problem at the table was ordinary and constant: character creation and rules lookups meant passing PDFs around and hunting through dense, extracted text for a table or a cross-reference nobody could find quickly.

Before writing a line of application code I also had a licensing line to hold: the book’s rules chapters — species, classes, combat, equipment, spells, the bestiary — are released under CC-BY-4.0 and fair game to transcribe as mechanics, but lore, setting text, and all artwork stay all-rights-reserved. Every later stage of the pipeline had to keep that distinction, not blur it.

Deliberately, I didn’t pick a stack on day one either. The plan was to audit the material first, define the first useful experience, and let that decide the architecture — not the other way around.

Getting the rules out of PDFs

The first real problem wasn’t which framework to use. It was that PDF extraction gives you words, not structure. The rulebook’s tables and multi-column layout came out of extraction with cells reassociated in ways that looked plausible and weren’t, and cross-references lost their anchors entirely. That’s a genuinely dangerous failure mode for a rules engine: a wrong number sitting quietly in a table becomes a real, silently broken game rule the moment something parses it straight into data nobody reviews.

My first instinct was the more direct path — parse the extracted text and fix records as errors turned up. That puts the review step after the data is already live in the app, which is backwards for a system where a broken formula changes what happens at an actual table. Instead I put a Markdown wiki between the PDFs and anything machine-readable: the PDFs stay the visual source of truth, the wiki is where a page gets checked against the source page by page, and dedicated converter scripts — wiki-to-rules-species.ts, wiki-to-rules-classes.ts, and later ones for backgrounds, items, and monsters — are the only thing allowed to turn reviewed wiki content into rules/crows/*.json compendium records. Pages still needing work stay explicit stubs, and the converters skip them rather than seeding the compendium with something that only looks finished.

PDF → reviewed Markdown → generated JSON became the shape everything else grew from. The wiki skeleton went in first — 100 pages across all ten of the book’s sections, mostly still stubs — with Backgrounds becoming the first section to get real content. Its many prose-based bonuses (“receive proficiency,” “once per day,” “maximum Favor is increased by 1”) turned into the first real test of whether the rules model could actually represent grants, choices, and limits, not just flat text.

The first time I looked at it

Before any of this had a UI, it had an API only. The first real milestone wasn’t a screen — it was one species (Akkedis) and one class (Fighter) transcribed all the way through, converted, and validated: a character-creation request now got rejected with a 400 if it named a species or class the compendium didn’t actually contain, and a real sheet came back computed from real ability scores instead of a stored placeholder. I checked it by hand before trusting it — HP 13, Mana 7, AC 13, proficiency bonus +1, all matching a hand-worked example from the book.

From there I built through essentially the rest of the planned system in one continuous push rather than one feature at a time with a UI check after each: the guided character-creation wizard, the sheet view, the searchable compendium browser, campaign tools, and a first version of the VTT — scenes, tokens, a WebSocket game channel, a combat tracker, walls, and fog of war — all landed together, verified at the API and WebSocket level with real tests and a real Docker build, but never yet looked at in an actual browser.

The six screenshots in this case study are the direct result of finally doing that — opening a browser and clicking through the whole thing for the first time, all captured in one sitting, right after that entire push landed. They aren’t an early, rough draft of the UI catching up to the backend piece by piece; they’re the first honest look at a system that had already been built end to end. And they earned their keep immediately: the very first pass through the VTT view found a real layout bug — its sidebar (combat tracker, chat, dice roller) was cut off past the edge of the viewport, because the app’s global content-width cap, fine for every other page, didn’t leave room for a battlemap canvas plus a 320px sidebar. I fixed it by letting that one route opt out of the width cap instead of loosening it for every page, then re-verified in a fresh session. The VTT screenshot below is from after that fix, which is why its full interaction surface actually fits inside the frame.

The other screenshots from that same session show a system whose UI was real but whose content was still narrow. The character builder’s species step is sparse because Akkedis was still the only fully transcribed species at that point — proof its options came from real compendium data rather than hardcoded UI choices, not yet proof of breadth. The compendium browser shows 59 total records — 57 backgrounds plus Akkedis and Fighter — with every other category (classes beyond Fighter, traits, feats, spells, items, monsters, conditions) sitting at zero. I left those empty counts visible rather than hiding them, because they were a more honest status report than any written note would have been: exactly how much of the pipeline worked, and exactly how much content was still missing.

Building character creation

Underneath all six of those screens sat the same generated data — the character builder’s species/class/background pickers, the sheet’s computed stats, and the compendium’s searchable list all read from the same rules/crows/*.json records produced by the wiki converters, not three separate implementations. The builder itself is a five-step wizard — species, class, ability scores, background, review — with scores assigned by rolling 6d4 and allocating per the book’s own method rather than a generic point-buy.

Broadening it past that first Akkedis/Fighter pair was mechanical repetition of the same converter pattern rather than new architecture: more species, more classes, then equipment and the bestiary once those chapters got their own transcription pass. Each addition landed the same way — wiki page reviewed against the source PDF, converter script run, seed script reloaded — and the builder and compendium picked it up automatically, since both already read from the same generated data rather than anything hardcoded per species or class. That repetition is also where a couple of real transcription bugs surfaced: a class-parser undercount that silently dropped a subclass Path from 11 of the 12 classes, and later a monster-stat-block parser whose label-matching regex quietly dropped an entire boss monster’s six-spell spell list because its heading had an unexpected parenthetical in it. Both were caught by actually inspecting the generated JSON output record by record, not by trusting that the conversion script ran without errors.

Building the character sheet

A character sheet that shows HP, Mana, AC, and proficiency bonus is only useful if those numbers are actually correct, and I didn’t want a second, hand-maintained copy of the book’s formulas living in application code that could quietly drift from the real rules. The obvious paths were hardcoding each formula as bespoke server logic per species/class, or reaching for a general rules-scripting DSL for maximum flexibility. Hardcoding doesn’t survive past the second or third species/class pair, and a full DSL is real power — and a real security surface, since a self-hosted tool now has to worry about what a scripting language can do — that the project didn’t actually need. Every formula the book uses, from HP per level to Mana to AC, fits a small expression grammar like 1dHD + con_mod. I built a sandboxed evaluator for exactly that grammar instead, with no arbitrary code execution, and every derived value on the sheet is now computed server-side from real ability scores and compendium data rather than re-entered anywhere.

The screenshot of Kassik, a level-one Akkedis Fighter, below is that formula grammar’s output: HP, Mana, AC, proficiency bonus, initiative, and passive perception all computed live, with the character’s species and class text pulled into the same view so the player doesn’t have to leave the sheet to remember what they can do.

That same honesty extended to what the formula grammar couldn’t cover. The book has you roll a hit die per level beyond the first, which is genuinely random, not a fixed formula. Rather than invent an average-roll convention the book never states, HP above level 1 deliberately isn’t computed at all yet — the sheet is correct about level 1 and honest about not yet supporting level-up, instead of quietly approximating something the rules don’t actually define.

Expanding into campaign management

Campaigns, journals, quests, and NPCs weren’t a separate feature phase so much as things that turned out to be missing the moment I actually tried to use the tool as a GM. Building the VTT push, for instance, needed a GM to see their own party’s characters in one place — an endpoint that simply didn’t exist yet, because nothing before that point had needed it. Journals split into GM-only and everyone-visible entries, filtered server-side rather than just hidden in the UI, and NPCs got the same treatment: a GM’s secret notes and a fully hidden NPC are stripped out of the response for a non-GM request before it ever leaves the server, not hidden behind a client-side flag a curious player could just inspect.

The project becomes a VTT

Scenes and tokens started as an extension of the same REST API — create a scene, create a token, patch its position — and that worked fine for authoring content alone. It stopped working the moment more than one person needed to see the same token move, the same fog reveal, or a combat turn advance, without everyone refreshing to find out. A normal request/response API doesn’t have anywhere to push a change to someone who didn’t ask for it.

I considered syncing raw client state over WebSockets and only validating it once it hit the REST layer, but that means trusting a player’s own browser about its own token ownership or vision radius — exactly the kind of thing that can’t hold up at a real table with real players. Instead every scene, token, chat message, dice roll, and fog reveal now travels as one intent over a per-campaign WebSocket channel (/api/ws/scenes/:id), rendered on a PixiJS canvas, and the server checks permission on every single message before it’s persisted or broadcast — not just once at connection time. Token ownership and vision radius are server-side fields the client is never trusted to assert about itself.

Improving the VTT

None of what follows is visible in the surviving screenshots — the one screenshot session was the baseline capture described above — but the project’s own build log documents a long, dated sequence of changes to the VTT afterward, so this is text evidence rather than visual evidence.

The right-hand rail was rebuilt from a fixed inventory panel into a contextual “GM Inspector” that follows whatever’s selected — a token, or nothing — and changes which tools are on screen accordingly. The action bar (Stride, Step, Strike, and so on) moved from firing immediately to a shared pending-action model, so starting an action no longer spends a resource before a destination or target has actually been chosen. Walls gained real movement-blocking, reusing the exact same segment-intersection check vision already used, just filtered by a different predicate — a window blocks vision but not movement, a closed door blocks both, only while it’s shut. A monster compendium arrived from transcribing the book’s nine-monster bestiary chapter, using the same wiki-to-rules pattern as everything else. And an attack-roll flow got wired end to end — target an enemy, roll against their real computed AC, apply damage, watch their HP actually drop in the chat log and on their token — deliberately kept generic, a typed dice expression rather than a per-weapon system, because no weapon or spell data existed in the compendium yet to make it any more specific than that.

Fog of war

Fog of war was the one place in the project with real, unavoidable geometry risk. The approach I actually wanted eventually is a true visibility-polygon sweep — the algorithm the more mature prior-art VTT projects use — but that’s substantial, non-trivial work on its own, and building it before anything else worked wasn’t the right order of operations. I shipped a simpler version first: for every grid cell inside a token’s vision radius, check whether there’s an unobstructed line to it against the scene’s drawn walls. That gave real wall-blocking and a permanent explored-memory layer immediately, which is most of what fog of war needs to feel right at the table, without the full sweep’s complexity — and I documented the upgrade path rather than quietly abandoning it.

According to the build log, that first pass later turned out to be mechanically fine but visually wrong: every unrevealed cell rendered as the same flat black rectangle, which conflated two genuinely different things — terrain explored before but not currently visible, and terrain never seen at all. That got split into three states instead: current line of sight at full brightness, explored-but-not-visible terrain as a dim memory layer, and truly unknown terrain nearly opaque, with tokens and dropped items tested for current visibility separately from the terrain memory underneath them, so an explored room doesn’t imply a creature is still standing in it.

Testing and hardening

The test suite grew in step with each layer rather than being bolted on afterward, because the failure modes were different at each layer and a green build doesn’t mean the same thing at all of them. REST endpoints got ordinary integration tests — permission checks, validation, the usual. The WebSocket layer needed something stronger: real ws client connections opening actual sockets against a running server, not a mocked transport, because the thing actually worth verifying was messages traveling through the same authorization path a real player’s browser would use — token movement and ownership, chat, dice rolls, combat turn order, and fog of war’s wall-blocking are all exercised this way. Fog of war specifically got unit tests on its segment-intersection logic before it was ever wired into a route, because a plausible-looking implementation could easily get the wall-blocking direction backwards, and a passing test catches that before it ever reaches a browser. On top of that, a full Docker build-and-run smoke test exercises migrations, the compendium seed, the API, and the served frontend together, so “the tests pass” and “a fresh deployment actually boots” are both checked, not assumed to imply each other.

Where it ended up

By the end of this build, the compendium holds 39 species, 12 classes, 57 backgrounds, 248 items, and 9 monsters, all generated from a 100-page Markdown wiki transcription rather than hand-typed. 67 tests pass across 15 files, including the live WebSocket integration tests described above. The architecture that got it there is a Fastify + WebSocket API over SQLite, a Vue 3 + Pinia + PixiJS frontend, and one command pipeline the VTT, combat tracker, and fog of war all flow through — none of it especially exotic on its own, but each piece exists because an actual problem at an actual table made the previous, simpler thing stop being enough.

What still isn’t finished

A few things are missing on purpose, not by oversight, and each is a real scope decision made in service of shipping a usable first release rather than a complete one.

HP beyond character level 1 isn’t computable, because the book has you roll a hit die per level and there’s no leveling-up flow yet to store those rolls — building that means real level-up state, not just a formula. A GM editing a player’s HP or conditions from the sheet doesn’t push a live update to that player’s own view, because only VTT-native state (tokens, combat, chat, fog) currently flows over the real-time channel — extending that to sheet-level edits means routing another whole class of change through the same command pipeline the VTT already uses. And campaign invitations are still a GM-adds-an-existing-user-by-email stand-in rather than real, time-limited invite codes, because building actual invitation codes is its own small feature — expiry, single-use redemption, revocation — that a friend-group deployment could defer without anyone actually being blocked by it. None of these are hidden; they’re the honest edge of what “done” currently means, and each is the obvious next thing to build if it ever becomes real friction at the table.
