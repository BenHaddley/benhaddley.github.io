Battle for North Africa

Creator · 2026 · 5 min read

A from-scratch digital engine for a WWII North Africa desert campaign wargame — real zone-of-control, supply attrition, and vehicle breakdown mechanics driving both a Tkinter desktop client and a web client from one shared rules core.

Overview

Battle for North Africa reimplements the core mechanics of a classic desert-warfare board wargame (the historical Commonwealth-vs-Axis campaign across Tripoli, Benghazi, Tobruk, and on to Alexandria) as a playable digital game. Real divisions — the 7th Armoured Division, 4th Indian Division, Ariete Armoured Division, 15th Panzer Division — move across a grid map built from real terrain costs, fight under zone-of-control and fog-of-war rules, and live or die by their supply lines, with a rules-driven AI opponent and both a desktop and browser-based way to play.

Problem

The board wargame this is based on is notorious for rules depth that goes far past "move a unit, roll a die" — supply lines determine whether an attack is even possible, terrain and zone-of-control constrain where a unit can legally go, armour and motorized units risk breaking down in bad terrain, and fog of war means you often don't know what you're facing until you're adjacent to it. Building a shallow version would have been easy; making all of those systems interact correctly — so that being cut off from supply, say, actually changes what a unit can do next turn — was the actual problem.

Constraints

  • The map's legal terrain and movement costs are derived from a plain-text ASCII map, so every rule (zone of control, breakdown risk, line-of-sight) has to work off simple character lookups rather than a richer map format
  • Zone-of-control has real exceptions baked into the source rules — a disorganized unit or a broken-down armour unit stops projecting ZOC — so it can't just check unit type
  • Supply and breakdown are turn-persistent state, not one-off checks: a unit that goes "Out of Supply" carries elevated breakdown risk and reduced capability into future turns
  • Two UIs (a Tkinter desktop client and a stdlib-only HTTP web client) both had to drive the exact same engine functions, so game logic couldn't leak into either UI layer
  • The four-phase turn structure (Organization → Truck Convoy Movement → Movement/Combat → Patrol) has to reset the right per-unit state at the right phase boundary, not just once per turn

Approach

The engine is a set of small, single-responsibility Python modules — grid/zone-of-control logic for movement legality, combat resolution, supply and breakdown/repair for logistics attrition, fog of war for visibility, objectives and phases for scoring and turn structure — all operating on a shared list of dataclass-based unit objects. An AI opponent uses the same public functions a human player's UI calls, so it can't cheat by reaching into state the rules wouldn't allow a player to touch. A rules-assistant lookup table surfaces plain-language rule explanations directly in the UI instead of requiring a rulebook. Once the Python/ASCII-map prototype validated the mechanics, work started on a React rewrite (bfna-modern) on a real hex grid, with browser-persisted saves and a guided-tour tutorial replacing the old text-based one.

Key Decisions

Decouple the engine from both UIs instead of building the rules into one interface

Reasoning:

Tkinter and a raw stdlib HTTP-based web client have almost nothing in common at the rendering layer. Keeping every rule in plain functions that only take/return unit and map data meant both UIs could call the identical attack/movement/supply functions and never risk disagreeing about what's legal.

Alternatives considered:
  • Build the web client first and treat the desktop client as a thin wrapper around it (or vice versa)
  • Duplicate core logic per UI and accept drift risk

Give the AI opponent no privileged access to game state

Reasoning:

The AI walks the same adjacency, movement-legality, and objective helpers a human player's UI action would call. That guarantees the AI is bound by the same zone-of-control, ammo, and CP constraints as a human, so its behavior stays a genuine test of the rules engine rather than a scripted illusion of an opponent.

Alternatives considered:
  • A scripted/faked AI that manipulates unit positions directly for simplicity

Start a React/hex-grid rewrite only after the Python/ASCII prototype proved the mechanics

Reasoning:

The original ASCII-character terrain map was fast to iterate on for validating rules like breakdown risk and ZOC, but isn't the interface a real player wants. Rather than build a polished frontend around unproven mechanics, the rewrite was started as a separate project once combat, supply, and breakdown were already working end-to-end in the Python prototype — moving to a proper hex grid and browser-persisted saves without re-deriving the rules from scratch.

Alternatives considered:
  • Build the modern frontend first and design rules against it directly
  • Keep iterating on the Tkinter/ASCII-map prototype indefinitely

Tech Stack

  • Python (dataclasses, enums)
  • Python stdlib http.server (web client)
  • Tkinter (desktop client)
  • React + Vite (bfna-modern rewrite)
  • react-hexgrid / honeycomb-grid
  • Zustand + idb-keyval (state and persisted saves)
  • driver.js (guided tutorial)

Result & Impact

The Python prototype is a fully playable two-sided game: a scripted historical scenario with real starting positions, a working AI opponent, save/load, an in-app rules assistant, and a guided tutorial mode — playable from either a desktop Tkinter window or a browser. The mechanics it validated (ZOC, supply attrition, breakdown/repair, fog of war) are now being carried into bfna-modern, a React/hex-grid rewrite aimed at replacing the ASCII map with a proper tactical grid UI.

Learnings

  • Decoupling rules from rendering early made the AI opponent, the rules assistant, and the second (web) UI all nearly free — none of them needed new game logic, just new callers of the same functions
  • State that persists across turns (supply status, broken-down vehicles) needs explicit phase-boundary reset logic, or effects meant to be "this turn only" silently carry forward
  • Validating game feel on a cheap-to-iterate representation before investing in a polished frontend meant the hex-grid rewrite could focus purely on presentation instead of also debugging mechanics
