DataToolKit

Creator · 2025 · 5 min read

A single desktop shell that auto-discovers and hosts 25+ standalone geospatial, OCR/translation, and computer-vision tools, unified behind one plugin architecture

Overview

A Tkinter desktop application that acts as a launcher and shared shell for a growing library of small, single-purpose data tools — geospatial mapping, image/EXIF geolocation, OCR and translation, and computer vision — without requiring each new tool to be wired into the shell by hand.

Problem

Useful one-off scripts (plot coordinates on a map, pull GPS out of a photo's EXIF data, OCR and translate an image, run zero-shot object detection) tend to stay scattered as separate files with no common entry point, no shared UI, and no easy way for someone else to discover what already exists.

Constraints

  • New tools need to be addable by dropping in a file, not by editing a central registry
  • Heavy ML dependencies (OCR models, translation models, object detection) can't slow down startup for tools that don't need them
  • Must work fully offline, including map tiles, since some environments have no reliable network access

Approach

Built a homepage shell that scans a folder for any file matching a naming convention, imports it, and reads a small metadata block to build the tool catalog automatically — turning 'add a tool' into 'add a file' with no shell changes required.

Key Decisions

Auto-discover tools by convention instead of a central registry

Reasoning:

Every file named *_app.py in the apps folder is imported and inspected for an APP_META dict (id, title, subtitle, category, icon code) and a factory function that builds its Tkinter frame. If both are present, the tool appears in the shell automatically — categorized by keyword rules (geospatial terms route to 'Geo / Mapping', image/CV terms to 'Computer Vision', and so on) with no manual wiring.

Alternatives considered:
  • A hand-maintained list of tools imported in the main shell file

Lazy-import heavy dependencies inside each tool, not at shell startup

Reasoning:

Libraries like torch, transformers, and easyocr are only imported the moment a specific tool is opened, so the shell itself starts quickly regardless of how many ML-heavy tools are registered.

Support an offline tile server for the mapping tools

Reasoning:

Both the coordinate-plotting and EXIF-geolocation tools read an optional environment variable for a custom map tile URL, so generated maps can render from a local tile cache instead of a public tile provider when there's no internet access.

Tech Stack

  • Python
  • Tkinter
  • OpenCV
  • Pillow (PIL)
  • Folium
  • EasyOCR / Transformers
  • PyInstaller / Inno Setup

Result & Impact

Turned a growing pile of separate scripts into one discoverable application — opening the shell shows every available tool without anyone needing to remember which script does what, and adding a new one is as simple as dropping in a correctly-shaped file.

Learnings

  • Convention-based plugin discovery scales much better than a manual registry once a tool count gets past a handful
  • Compositing a video frame every tick is expensive enough to matter — resizing and cropping before blending keeps frame time predictable
  • Deferring heavy imports until a tool is actually opened is a simple, high-leverage way to keep a large multi-tool app feeling lightweight

Workflow: geospatial tools

Two of the plugin tools cover the “point on a map” problem from opposite directions:

  • Cora Plot takes a CSV or Excel file, lets the user pick which columns hold latitude and longitude, and generates an interactive Folium map — with GeoJSON export for use elsewhere.
  • Image Coordinate Viewer goes the other way: given a folder of photos, it reads each image’s EXIF GPSInfo block, converts the GPS degrees/minutes/seconds rational values into decimal-degree floats, builds a table of coordinates and timestamps, and plots every geotagged photo on a Folium map opened straight in the browser.

Both share the same rendering path — build the map as HTML via Folium, then hand it to the system browser — so neither tool needed its own map-rendering code.

Workflow: the RGBA animated background

The shell’s homepage isn’t a static image — it’s a looping video rendered as an animated, alpha-blended background behind the tool grid, and getting that onto a Tkinter canvas (which has no native video support) is its own small pipeline:

  1. Decode a frame. OpenCV (cv2.VideoCapture) reads the next video frame as a BGR NumPy array, timed against the source video’s own frame rate so playback speed matches the original.
  2. Convert color space and mode. The frame is converted from OpenCV’s BGR channel order to RGB, then loaded into Pillow and converted to RGBA — adding the alpha channel needed for the next step.
  3. Cover-fit to the window. The frame is scaled and center-cropped to fill the current window size exactly (the same “cover” behavior as CSS background-size: cover), so the video fills the pane regardless of window aspect ratio.
  4. Alpha-composite a dark overlay. A solid black RGBA image is generated at the same size with a fixed alpha value, and Image.alpha_composite() blends it over the video frame. This is what darkens the footage enough for the UI text and tool icons drawn on top to stay readable — without it, a bright video frame would wash out the interface.
  5. Hand off to Tkinter. The composited RGBA image is converted to a PhotoImage and drawn on the canvas, replacing the previous frame; the loop reschedules itself at the video’s frame interval, and loops back to the start when the clip ends.

The same RGBA-composite step (decode/convert → cover-fit → alpha blend) is reused for a static fallback image when no video is available or OpenCV can’t be loaded, so the shell degrades gracefully instead of failing to render a background at all.
