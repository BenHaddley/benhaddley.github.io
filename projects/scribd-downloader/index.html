Scribd PDF Downloader

Creator · 2026 · 5 min read

A Chromium extension that adds a one-click Download PDF button to Scribd, reconstructing any public document as a real PDF from Scribd's own page images — no account, subscription, or server required

Overview

A Manifest V3 browser extension that injects a Download PDF button into Scribd document pages. Clicking it reassembles the document from Scribd's public page-image tiles into a genuine downloadable PDF, entirely inside the browser.

The button (top right, red) as it actually appears — injected live onto a real, public Scribd document page, no server or account involved.

Problem

Scribd renders documents as a stream of page images behind a paywall-gated 'Download' flow that requires an account, credits, or a subscription. The underlying page images, however, are already public — served straight from Scribd's own screenshot CDN with no auth. The goal was to turn what the browser already loads into a portable file, without scraping credentials, a backend, or a paid API.

Constraints

  • No server or account — everything has to run from the extension itself, in the browser
  • Must respect CORS realities: page scripts can't fetch cross-origin screenshot URLs, so that work has to happen where extension host_permissions apply
  • No external PDF library — the PDF has to be built by hand to keep the extension dependency-free and auditable
  • Needs to survive large documents (100s of pages) without freezing the tab or blowing up memory in the page context

Approach

content.js extracts the document id, page count, and screenshot base URL straight out of Scribd's own reader bootstrap data and injects a floating Download PDF button. Clicking it hands off to background.js (the MV3 service worker), which spins up a short-lived offscreen document — the one MV3 context that can both hold host_permissions-backed fetches and build a Blob. offscreen.js fetches every page image with 6 concurrent workers, streams progress back to the button label, then pdf-builder.js assembles a valid PDF 1.4 file by hand, embedding each JPEG directly via DCTDecode with no re-encoding. The finished blob is handed back to the service worker, which triggers the actual browser download.

Key Decisions

Do the fetching in an offscreen document, not the content script or service worker directly

Reasoning:

Content scripts run in the page's isolated world and are subject to the page's CORS policy, so they can't pull cross-origin screenshot images. Service workers in MV3 have no DOM/Blob-friendly context for assembling a large file. An offscreen document is the one place that has both DOM APIs and inherits the extension's host_permissions, letting fetches to screenshots.scribd.com bypass CORS entirely.

Alternatives considered:
  • Fetch from the content script (blocked by CORS)
  • Proxy every image through a backend server (reintroduces the exact server dependency the project was trying to avoid)

Write a minimal PDF encoder by hand instead of pulling in a PDF library

Reasoning:

Each page is already a JPEG, and PDF's DCTDecode filter can embed a JPEG byte-for-byte with no re-encoding — so a full library like pdf-lib is unnecessary weight for what's really just XObject/image placement and a page tree. Keeping it dependency-free also means the whole extension is a handful of files a reviewer can read end to end before granting it host permissions.

Alternatives considered:
  • Bundle a third-party PDF library

Extract document metadata (id, page count, image base URL) from the page itself rather than calling a Scribd API

Reasoning:

Scribd's reader already embeds the document id, allowedPagesTemp page list, and thumbnail URLs in the page's own bootstrap script and DOM. Reading that directly avoids reverse-engineering any private endpoint or auth flow — the extension only ever touches URLs the page was already going to load.

Tech Stack

  • Chrome Extension Manifest V3
  • Offscreen Documents API
  • Vanilla JavaScript (no dependencies)
  • chrome.downloads API
  • Hand-written PDF 1.4 encoder

Result & Impact

Turns any public Scribd document into a portable, offline-readable PDF in a few seconds with a single click, with no account creation, no subscription, and no server in the loop.

Learnings

  • MV3's split between service workers, content scripts, and offscreen documents forces you to think in terms of which context actually has which capability (DOM vs. host_permissions vs. persistence) rather than writing one script that does everything
  • A lot of paywalled 'download' flows are gating a UI action, not the underlying data — the images were already being sent to the browser either way
  • Reconstructing a well-known file format by hand (PDF, in this case) is far more approachable than it looks once you only need the one feature path (JPEG-backed image pages) rather than the whole spec

Architecture

The extension is split across MV3’s three execution contexts, each used for what it alone can do: content.js reads page metadata and renders the button in the page’s isolated world; background.js (the service worker) brokers messages and owns the final chrome.downloads call, since that’s the documented pattern for large MV3 downloads; and a transient offscreen.js document does the actual cross-origin fetching and PDF assembly, closing itself once the download starts.

Page fetching

offscreen.js runs a small worker-pool fetcher — 6 concurrent workers pulling from a shared queue of page numbers — against https://screenshots.scribd.com/Scribd/252_100_85/324/<docId>/<n>.jpeg, reporting progress back to the toolbar button every 10 pages so a 600-page document doesn’t look frozen.

PDF assembly

pdf-builder.js is a standalone, dependency-free PDF 1.4 writer: it reads each JPEG’s dimensions directly from its header, lays out an XObject/page tree, and embeds the JPEG bytes unmodified via the DCTDecode filter — so building a 300-page PDF is just concatenating already-downloaded bytes with a thin structural wrapper, not re-encoding a single pixel.

Limitations

Public screenshots top out at 252px wide — Scribd’s only unauthenticated resolution — so output is readable but not print-quality, and documents whose screenshots aren’t public have those pages silently skipped rather than failing the whole download.
